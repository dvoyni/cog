# 2D prior art: Unity, Godot, Bevy, MonoGame and raylib

Research for [#861](https://github.com/dvoyni/cog/issues/861), on the map [#860](https://github.com/dvoyni/cog/issues/860). It asks how other engines shape 2D materials, sprites, cameras and batching, and what each choice costs: what a 2D material may replace, how per-sprite data reaches the shader, whether sprites, text and meshes share one material model, how draws are ordered and batched, what the 2D camera offers, and how an outline, a glow or a dissolve is made. It records facts and decides nothing for 2D. The last sections relate them to WebGPU and to v1's lessons.

## In short

- **A 2D material may replace both stages in Godot and Bevy, and only the graph's blocks in Unity's Shader Graph.** Godot's `canvas_item` shader has `vertex()`, `fragment()` and `light()`, each spliced into the engine's own `canvas.glsl`. The engine keeps the per-instance record, the vertex inputs and the transform (`skip_vertex_transform` hands the transform over). Bevy's `Material2d` names a vertex and a fragment shader over a `Mesh2d`, and since 0.20 a `MaterialExtension2d` does the same for sprites. Unity's Sprite Unlit, Sprite Lit and Sprite Custom Lit targets expose vertex position, normal and tangent, and fragment color, alpha, alpha clip, mask and normal. A hand-written ShaderLab sprite shader replaces everything but must read the `SpriteRenderer`'s mesh and its per-draw constants. MonoGame and raylib take a whole shader program over a fixed vertex format.
- **No engine lets a user add a member to the per-sprite record. Each offers a small side channel instead.** Unity 6.3 gives each renderer one 32-bit "Renderer Shader User Value". Bevy gives each mesh one `u32` `MeshTag`, which `GpuComponentArrayBuffer` turns into an index into a user storage buffer. Godot gives up to 16 scalar or vector `instance uniform`s per shader, stored in a global buffer at an offset each instance carries. MonoGame and raylib offer only the vertex color.
- **Bevy 0.20 moved a sprite's tint, flip and rectangle out of the instance and into a material.** `Sprite` now renders as a `Mesh2d` quad with a `SpriteMeshMaterial`, cached per distinct sprite value. Without bindless, which needs wgpu's native-only `TEXTURE_BINDING_ARRAY`, each such material is its own bind group, and a bind group change breaks the batch. Text2d still uses the older instanced sprite pipeline.
- **Sprites, text and meshes share one material model in Godot, raylib and MonoGame, and not in Unity or Bevy.** Godot's glyphs, rects, polygons and meshes are all canvas item commands under the item's one `material`. Unity's TextMesh Pro has its own signed distance field (SDF) shaders and materials. Bevy's `Text2d` takes no material at all.
- **Order is a few integer keys, then painter's order.** Unity sorts by sorting layer, order in layer, render queue, then distance along a configurable axis, which is its Y-sort. Godot sorts by `CanvasLayer`, then a `z_index` in −4096…4096, then tree order, or Y under a `y_sort_enabled` parent. Bevy has only the translation's `z` (plus a material's `depth_bias`). MonoGame has a float layer depth. raylib has call order.
- **A batch is a run of consecutive draws that share what the GPU must rebind.** Godot breaks on a change of material, texture, clip rectangle, lighting, command type, MSDF parameters, or at any mesh. Bevy breaks on a change of pipeline, draw function, mesh or material bind group. MonoGame breaks on texture, and raylib on texture, shader, blend mode, camera or scissor. Each sorts before batching, so a batch never reorders draws.
- **The 2D camera is an orthographic view with a zoom, plus some notion of a logical resolution.** Bevy's `ScalingMode` has six modes (`WindowSize`, `Fixed`, `AutoMin`, `AutoMax`, `FixedVertical`, `FixedHorizontal`), and cameras have viewports, an `order` and render layers. Godot's `Camera2D` sets the viewport's canvas transform, one per viewport, and the project's stretch mode, aspect and integer scale give the logical resolution. Unity's Pixel Perfect Camera adds crop frames, pixel snapping and an upscaled render texture. Bevy has no pixel-perfect camera: its example renders to a 160×90 image and upscales it with a second camera.
- **A sprite outline is a material everywhere, and a text outline is a feature.** No engine has a sprite outline component: it is a fragment shader that samples neighbouring alpha, and it can only draw inside the quad unless the vertex stage grows it. Text outlines are built in. Godot's `Label` draws every outline glyph of a line before every fill glyph, as a separate run of draws. TextMesh Pro's SDF material has outline, underlay and glow properties. Bevy's `Text2dShadow` draws extra glyph sprites. Glow is HDR plus a bloom post effect in all three big engines. A dissolve is a material.

## 1. What a 2D material may replace

| | Unity URP 2D | Godot 4.7 | Bevy 0.20 | MonoGame | raylib |
|---|---|---|---|---|---|
| **The user writes** | a ShaderLab shader, or a Shader Graph with a Sprite Unlit, Sprite Lit or Sprite Custom Lit target | a `shader_type canvas_item` with `vertex()`, `fragment()`, `light()` | a `Material2d`'s `vertex_shader()` and `fragment_shader()` in WGSL/WESL, or a `MaterialExtension2d` over a sprite | an `Effect` passed to `Begin` | a `Shader` from `LoadShader(vs, fs)` |
| **Vertex stage** | Shader Graph: position, normal, tangent blocks. ShaderLab: all of it | `VERTEX` in local pixels; `world_vertex_coords` or `skip_vertex_transform` change who transforms it | the whole vertex function over the mesh's attributes | the effect's vertex shader if it has one; otherwise `SpriteEffect`'s stays bound | the whole vertex shader, over the fixed attribute names |
| **Fragment stage** | Shader Graph: base color, sprite color, alpha, alpha clip, mask, normal blocks | `COLOR`, `NORMAL`, `NORMAL_MAP`, plus `light()` per light | the whole fragment function | the whole pixel shader | the whole fragment shader |
| **Fixed around it** | queue Transparent, the sprite's mesh, its per-draw constants (`UnityPerDraw`), sorting, the 2D lighting passes | `InstanceData`, the vertex inputs, set 0 globals, set 2 transforms, set 3 textures; blend via `render_mode` | group 0 view, group 1 per-mesh array, the phase (from `alpha_mode`), the sort; `specialize()` may edit the pipeline descriptor | `VertexPositionColorTexture`, texture slot 0 | the vertex layout, `mvp`, `colDiffuse`, `texture0` |
| **Its parameters** | `UnityPerMaterial` constant buffer | set 1: one `MaterialUniforms` block plus textures | group 2: an `AsBindGroup` struct | effect parameters | uniforms set with `SetShaderValue` |

### Unity URP 2D

- **Default shaders.** `Sprite-Unlit-Default` is queue `Transparent`, `Blend SrcAlpha OneMinusSrcAlpha`, `Cull Off`, with `ZWrite` a material toggle. Its vertex function flips the position by `unity_SpriteProps` and outputs `input.color * _Color * unity_SpriteColor`. Its `UnityPerMaterial` holds only `_Color`, with a note that properties must not be `#ifdef`ed "as SRP batcher can not handle different layouts". ([Sprite-Unlit-Default.shader#L17–L65](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Shaders/2D/Sprite-Unlit-Default.shader#L17)) `Sprite-Lit-Default` adds the 2D lighting passes. `Mesh2D-Lit-Default` and `Mesh2D-Unlit-Default` exist for mesh renderers drawn by the 2D renderer. ([Shaders/2D](https://github.com/Unity-Technologies/Graphics/tree/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Shaders/2D))
- **Shader Graph sprite targets.** Sprite Unlit's blocks are vertex Position, Normal and Tangent, and fragment Sprite Color and Alpha Clip Threshold, plus Base Color and Alpha. The render queue is Transparent. ([UniversalSpriteUnlitSubTarget.cs#L63](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Editor/2D/ShaderGraph/Targets/UniversalSpriteUnlitSubTarget.cs#L63)) Sprite Custom Lit adds Sprite Mask and Normal (Tangent Space) and its own "Sprite Lit", "Sprite Normal" and "Sprite Forward" passes. ([UniversalSpriteCustomLitSubTarget.cs#L46](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Editor/2D/ShaderGraph/Targets/UniversalSpriteCustomLitSubTarget.cs#L46)) So a graph moves vertices and colours fragments; the passes, the blend and the queue are the target's.

### Godot

- **Built-ins and stages.** `vertex()` sees `VERTEX` (a `vec2`), `UV`, `COLOR`, `POINT_SIZE`, `MODEL_MATRIX`, `CANVAS_MATRIX`, `SCREEN_MATRIX`, `INSTANCE_CUSTOM`, `INSTANCE_ID`, `VERTEX_ID`, `CUSTOM0` and `CUSTOM1`. `fragment()` sees `COLOR`, `TEXTURE`, `TEXTURE_PIXEL_SIZE`, `UV`, `NORMAL`, `NORMAL_MAP`, `SCREEN_UV`, `SCREEN_PIXEL_SIZE`, `REGION_RECT`, `POINT_COORD` and the SDF functions. `light()` sees the light's colour, position, direction and energy, and `SHADOW_MODULATE`. The render modes are `skip_vertex_transform`, `blend_{mix,add,sub,mul,premul_alpha,disabled}`, `unshaded`, `light_only` and `world_vertex_coords`. ([shader_types.cpp#L269–L363](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/shader_types.cpp#L274))
- **Semantics.** `VERTEX` is "pixel coordinates, relative to the Node2D's origin". In `vertex()`, `COLOR` is "the color from the vertex primitive multiplied by the CanvasItem's modulate multiplied by the CanvasItem's self_modulate". In `fragment()`, it is that times the `TEXTURE` sample. `REGION_RECT` is the visible area of a sprite region. A `light()` function "will replace the built-in light function, even if your light function is empty". `SCREEN_TEXTURE` was "Removed in Godot 4" in favour of a `sampler2D` with `hint_screen_texture`. ([CanvasItem shaders, 4.7](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/canvas_item_shader.html))
- **The engine's frame around it.** The user's code goes into `#CODE : VERTEX`, `#CODE : LIGHT` and `#CODE : FRAGMENT` in `canvas.glsl`, and its uniforms into `layout(set = 1, binding = 0) uniform MaterialUniforms`. ([canvas.glsl#L109](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas.glsl#L109), [#L274](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas.glsl#L274), [#L701](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas.glsl#L701)) The fixed sets are set 0 for globals (`CanvasData`, lights, atlases, the SDF texture, global shader uniforms), set 1 "reserved for the material", set 2 for instancing and skeletons, and set 3 for the item's color, normal and specular textures and sampler. ([canvas_uniforms_inc.glsl#L118–L203](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas_uniforms_inc.glsl#L118)) The built-in `TEXTURE` is renamed to `color_texture`, set 3's binding. ([renderer_canvas_render_rd.cpp#L1793](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L1793))
- **Two kinds of material.** `CanvasItemMaterial` has only `blend_mode`, `light_mode` and particle-animation settings, and "Use a [ShaderMaterial] to more fully customize". ([CanvasItemMaterial.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CanvasItemMaterial.xml#L7)) A `CanvasItem` has one `material`, and `use_parent_material` takes its parent's. ([CanvasItem.xml#L665](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CanvasItem.xml#L665), [#L691](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CanvasItem.xml#L691))

### Bevy

- **`Material2d`.** "Materials must implement `AsBindGroup`", and every function has a default. The trait has `vertex_shader()`, `fragment_shader()` (each `ShaderRef::Default` unless overridden), `depth_bias()`, which is added to the sort key, `alpha_mode()` (`Opaque` by default), and `specialize()`, which may edit the `RenderPipelineDescriptor`. In WGSL the material sits at `@group(2)`. ([mesh2d/material.rs#L74–L193](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/material.rs#L148)) `AlphaMode2d` is `Opaque`, `Mask(f32)` or `Blend`. ([#L260](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/material.rs#L260)) Group 0 is the `View`, and group 1 is the per-mesh array. ([view_bindings.wesl](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/view_bindings.wesl), [bindings.wesl](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/bindings.wesl))
- **Sprite materials, new in 0.20.** "Until now, Bevy's sprite renderer has been lacking a major feature: the ability to extend it with custom shaders!" A user implements `MaterialExtension2d`, inserts `SpriteMaterial<M>` and adds `SpriteMaterialPlugin<M>`. ([0.20 notes](https://bevy.org/news/bevy-0-20/)) The extension may override the vertex shader, the fragment shader, the depth bias and the alpha mode, and its bindings must sit above the sprite's ("Make sure to use a high enough uniform to avoid colliding with the sprite's bindings", `#[uniform(20)]` in the example). A fragment override may call `sample_final_color`, `sample_sprite_texture` and `get_final_color` from `sprite_mesh::functions`. ([sprite_extended_material.rs#L161–L214](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/sprite_mesh/sprite_extended_material.rs#L161))
- **Low level.** The `mesh2d_manual` example renders 2D items with a custom pipeline "without the `Material2d` abstraction", to change the vertex buffer. ([mesh2d_manual.rs](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/examples/2d/mesh2d_manual.rs#L1))

### MonoGame and raylib

- **MonoGame.** `Begin(sortMode, blendState, samplerState, depthStencilState, rasterizerState, effect, transformMatrix)`: the effect is "A custom Effect to override the default sprite effect". ([SpriteBatch.cs#L66–L79](https://github.com/MonoGame/MonoGame/blob/76ed1c24f7dbe91421023c553978fa723548b22a/MonoGame.Framework/Graphics/SpriteBatch.cs#L66)) `Setup` always applies the default `SpriteEffect` pass first (`_spritePass.Apply()`), and each flush then applies every pass of the custom effect. ([SpriteBatch.cs#L127–L136](https://github.com/MonoGame/MonoGame/blob/76ed1c24f7dbe91421023c553978fa723548b22a/MonoGame.Framework/Graphics/SpriteBatch.cs#L127), [SpriteBatcher.cs#L242](https://github.com/MonoGame/MonoGame/blob/76ed1c24f7dbe91421023c553978fa723548b22a/MonoGame.Framework/Graphics/SpriteBatcher.cs#L242)) So an effect with only a pixel shader keeps the default vertex shader and its matrix. The default effect is one `MatrixTransform` and `SAMPLE_TEXTURE(Texture, uv) * color`. ([SpriteEffect.fx](https://github.com/MonoGame/MonoGame/blob/76ed1c24f7dbe91421023c553978fa723548b22a/MonoGame.Framework/Platform/Graphics/Effect/Resources/SpriteEffect.fx#L29)) The effect is fixed from `Begin` to `End`.
- **raylib.** A shader binds by fixed attribute names (`vertexPosition`, `vertexTexCoord`, `vertexColor` and more) and uniform names (`mvp`, `colDiffuse`, `texture0`). ([rlgl.h#L62–L81](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rlgl.h#L62)) `BeginShaderMode` swaps the program, and `rlSetShader` flushes the batch when it changes. ([rcore.c#L1058](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rcore.c#L1058), [rlgl.h#L4592](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rlgl.h#L4592))

## 2. Per-sprite data, and adding to it

| | Unity URP 2D | Godot 4.7 | Bevy 0.20 | MonoGame | raylib |
|---|---|---|---|---|---|
| **The record** | vertex color, plus `unity_SpriteColor` and `unity_SpriteProps` (flip, skinning offsets) in `UnityPerDraw`, or in the `PerDrawSprite` instancing buffer | `InstanceData`: 2×3 transform, modulate, nine-patch margins, destination and source rectangles, flags, instance-uniform offset, four light indices | `Sprite`: none per instance; tint, flip, rectangle and slicing live in the `SpriteMeshMaterial` uniform. Per mesh: `Mesh2d` (transform, flags, material slot, tag, metadata index) | four `VertexPositionColorTexture`s | per vertex: position, texcoord, color |
| **How it arrives** | per-draw constants; the comment "SpriteRenderer.Color while Non-Batched/Instanced" | instance-rate vertex attributes at locations 8–15, plus a push constant per batch | a storage array `array<Mesh2d>` read at `instance_index` | CPU-built vertices | CPU-built vertices |
| **User addition** | one 32-bit Renderer Shader User Value (6.3+); per-sprite-asset vertex attributes; `MaterialPropertyBlock` (breaks SRP batching) | up to 16 `instance uniform`s, scalar or vector, no textures or arrays; `INSTANCE_CUSTOM` for MultiMesh and particles; `CUSTOM0`/`CUSTOM1` mesh attributes | one `u32` `MeshTag`; `GpuComponentArrayBuffer<C>` keeps a storage buffer of `C` and writes each entity's index into its tag | the vertex color | the vertex color |
| **Batch cost** | RSUV "doesn't interfere with batching" | none: the offset is per instance | none for the tag; the component buffer is a binding of the material | n/a | n/a |

### Unity

- **Where sprite color and flip live.** `unity_SpriteColor` and `unity_SpriteProps` (X: fat vertex stride and the flip bits, Z: bone matrix offset, W: unified deform offset) are declared inside `CBUFFER_START(UnityPerDraw)`, beside `unity_RendererUserValue = asuint(unity_RenderingLayer.y)`. ([UnityInput.hlsl#L78–L149](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/ShaderLibrary/UnityInput.hlsl#L136)) Under instancing they come from `UNITY_INSTANCING_BUFFER_START(PerDrawSprite)` arrays instead, with the comment "SpriteRenderer.Color while Non-Batched/Instanced". ([Core2D.hlsl#L141–L160](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Shaders/2D/Include/Core2D.hlsl#L141)) The default shader also multiplies the vertex color. That is three paths for one tint, picked by how the engine batched the sprite.
- **Renderer Shader User Value (RSUV).** "RSUV is a custom 32-bit integer value that you can assign to each renderer to provide specific data to the shader." `SpriteRendererDataAccessExtensions.SetShaderUserValue(uint)` sets it on a sprite renderer, and HLSL reads `unity_RendererUserValue`. "This functionality doesn't interfere with batching." It is SRP-only, and "RSUV usage and encoding are shader-specific". ([RSUV introduction, 6000.6](https://docs.unity.com/en-us/engine/current/manual/materials-and-shaders/shaders/renderer-shader-user-value/intro))
- **Per-asset vertex data.** `SpriteDataAccessExtensions.SetVertexAttribute` "Sets a specific channel of the VertexAttribute" of a `Sprite`, which every renderer of that sprite shares. ([SpriteDataAccessExtensions, 6000.3](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/u2d/spritedataaccessextensions))
- **Property blocks.** An SRP-Batcher-compatible object "mustn't use MaterialPropertyBlocks". ([SRP Batcher compatibility, 6000.2](https://docs.unity3d.com/6000.2/Documentation/Manual/SRPBatcher-Materials.html))

### Godot

- **`InstanceData`** is `world_x`, `world_y`, `world_ofs`, `ninepatch_pixel_size`, then for a rect `modulation`, `ninepatch_margins`, `dst_rect` and `src_rect` (for a primitive, three points, UVs and packed colours), then `flags`, `instance_uniforms_ofs` and `uvec4 lights`. ([canvas_uniforms_inc.glsl#L19](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas_uniforms_inc.glsl#L19)) The vertex shader reads it as instance attributes `attrib_A` … `attrib_H` at locations 8–15 and passes a flat copy to the fragment stage. ([canvas.glsl#L58](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas.glsl#L58)) Meshes, MultiMeshes and particles read the same fields from the push constant `Params` instead, under `USE_ATTRIBUTES`. ([canvas_uniforms_inc.glsl#L51](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas_uniforms_inc.glsl#L51))
- **Instance uniforms.** "Per-instance uniforms are available in both `canvas_item` (2D) and `spatial` (3D) shaders". They "do not support textures or arrays, only regular scalar and vector types", and there is "a practical maximum limit of 16 instance uniforms per shader". ([Shading language, 4.7](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/shading_language.html)) A uniform is "assignable on a per-instance basis" only when declared `instance uniform`, and set with `CanvasItem.set_instance_shader_parameter`. ([CanvasItem.xml#L615](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CanvasItem.xml#L615)) The compiler reads them from `global_shader_uniforms.data` at `read_draw_data_instance_offset`, and each instance carries its own offset, so a batch need not break. ([renderer_canvas_render_rd.cpp#L1847](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L1847), [#L2358](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L2358))

### Bevy

- **The old instance record.** The instanced sprite pipeline's `SpriteInstance` is a 3×4 transposed affine, a colour and `uv_offset_scale`, 80 bytes in an instance-rate vertex buffer. The quad comes from `vertex_index`. ([render/mod.rs#L364](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/render/mod.rs#L364), [sprite.wesl](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/render/sprite.wesl)) In 0.20 only `Text2d` (with its shadow) still fills it. ([text2d/mod.rs#L98](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/text2d/mod.rs#L98))
- **Sprites as meshes.** "The sprite render backend was replaced by a new backend that reuses a lot of the infrastructure made for 3D." ([0.20 notes](https://bevy.org/news/bevy-0-20/)) `SpriteMeshPlugin` inserts one shared unit-quad `Mesh2d` on each added `Sprite`, and a `MeshMaterial2d<SpriteMeshMaterial>` built from the sprite. ([sprite_mesh/mod.rs#L61](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/sprite_mesh/mod.rs#L61), [#L176](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/sprite_mesh/mod.rs#L176)) Materials are cached by a key of image, atlas layout, colour, flips, custom size, rectangle, alpha mode and anchor, and evicted when no entity holds them. ([#L84](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/sprite_mesh/mod.rs#L84)) The material's uniform holds colour, flags, alpha cutoff, `vertex_scale`, `vertex_offset`, a `uv_transform` and the tiling and slicing values. It is bindless-capable, `#[bindless(index_table(range(0..3)))]` with `binding_array(10)`. ([sprite_mesh_material.rs#L32–L96](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/sprite_mesh/sprite_mesh_material.rs#L32), [bindings.wesl](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/sprite_mesh/bindings.wesl))
- **Per mesh.** `Mesh2d` in WGSL is `world_from_local`, the inverse transpose, `flags`, `material_bind_group_slot`, `tag` and `metadata_index`, read from `@group(1) @binding(0) var<storage> mesh: array<Mesh2d>` (a uniform array at a dynamic offset where storage buffers are missing). ([types.wesl](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/types.wesl), [bindings.wesl#L4](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/bindings.wesl#L4)) `get_tag(instance_index)` reads the tag. ([functions.wesl#L46](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/functions.wesl#L46))
- **User data.** `MeshTag` is "the value made available to the shader". A `GpuComponentArrayBuffer` maintains it: "If you aren't using a `GpuComponentArrayBuffer`, the tag is free for you to use for whatever purpose you wish." ([components.rs#L190–L208](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_mesh/src/components.rs#L190)) `GpuComponentArrayBuffer` is "Lightweight storage of per-mesh-instance data": it packs a component into a `ShaderBuffer`, keeps an entity-to-index map, swap-removes on despawn, and rewrites the displaced entity's tag. ([gpu_component_array_buffer.rs](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/gpu_component_array_buffer.rs#L1), [example](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/examples/shader/gpu_component_array_buffer.rs#L1))

## 3. Sprites, text and meshes: one material model or several

| | Sprites | Text | Custom meshes | One model? |
|---|---|---|---|---|
| **Unity** | `SpriteRenderer` with sprite shaders or Sprite Shader Graph targets | TextMesh Pro: its own SDF shaders and materials | `MeshRenderer` with `Mesh2D-*` or any shader | no |
| **Godot** | `Sprite2D`: a rect command | `Label`: rect commands over the font's cache texture, MSDF or bitmap | `Polygon2D`, `MeshInstance2D`, `MultiMeshInstance2D` | yes: one `canvas_item` shader type and one `material` per item |

- **Godot.** A `Label`'s glyphs are rect commands whose texture is the font cache texture, flagged MSDF or not, so they go through `canvas.glsl` like any sprite. - **Bevy.** `queue_sprites` still queues the extracted (text) sprites into `Transparent2d` beside `queue_material2d_meshes`. ([lib.rs#L99](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/lib.rs#L99)) Glyphs are rasterised into `FontAtlas`es keyed by font, face index, size bits and variation hash, so they are bitmap glyphs per size. ([font_atlas_set.rs#L12](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_text/src/font_atlas_set.rs#L12)) `TilemapChunk` is a `Mesh2d` with its own material, `TilemapChunkMaterial`. ([tilemap_chunk](https://github.com/bevyengine/bevy/tree/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/tilemap_chunk))

([rtext.c#L1282](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rtext.c#L1282)) `FONT_SDF` generation "requires external shader", which the `text_font_sdf` example supplies. ([raylib.h#L913](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/raylib.h#L913), [text_font_sdf.c](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/examples/text/text_font_sdf.c))

## 4. Order and batching

| | Unity URP 2D | Godot 4.7 | Bevy 0.20 | MonoGame | raylib |
|---|---|---|---|---|---|
| **Order keys** | sorting layer → order in layer → material render queue → distance (camera, or a custom axis) → material groups → internal | `CanvasLayer.layer` → `z_index` (−4096…4096, relative to the parent by default) → tree order, or Y under a `y_sort_enabled` parent (ties by tree index) | translation `z` (+ `depth_bias`) in `Transparent2d`; opaque and masked meshes binned with a depth buffer | `layerDepth` in `BackToFront` or `FrontToBack` (unstable sort), or call order (`Deferred`), or texture (`Texture`) | call order; each vertex gets a depth 1/20000 above the last |
| **Groups that keep together** | Sorting Group | `CanvasGroup` (draws children through the backbuffer); `CanvasLayer` | none | one `Begin`/`End` | none |
| **A batch breaks on** | engine-side: not documented beyond material, texture and shader compatibility | clip owner, material, lighting on or off, command type, LCD blend, MSDF range or outline, texture state, a mesh, a full instance buffer | pipeline, draw function, mesh, material bind group; any non-sprite item between instanced sprites | texture; `Immediate` draws each sprite alone | texture, shader, blend mode, `BeginMode2D`, scissor, a full buffer |
| **Batch limit** | engine-side | `rendering/2d/batching/item_buffer_size` = 16384 | buffer growth | `short.MaxValue / 6` quads per draw | `RL_DEFAULT_BATCH_BUFFER_ELEMENTS` = 8192 quads, 256 draw calls |

### Unity

- **The documented order.** 1 sorting layer ("earlier if its Sorting Layer is higher in the list"), 2 order in layer, 3 the material's render queue, 4 distance, which "depends on the Projection property of the camera, the Transparency Sort Mode property, and the Sort Point", 5 "Shader and material properties: Unity renders GameObjects with the same shader and material properties together in a group. The order Unity uses to render the different groups isn't guaranteed." The tiebreaker "isn't guaranteed and you can't control it". A Sorting Group "renders as one unit on a single sorting layer and sublayer". ([2D rendering order, 6000.6](https://docs.unity.com/en-us/engine/6000.6/manual/unity2d/sprite/sort-sprites/sort-sprites))
- **Y-sort.** Set Transparency Sort Mode to Custom Axis: "(0, 1, 0) so the higher the GameObject in the scene, the further away it is. This is useful for top-down games", and (1, 1, 0) for isometric. All 2D materials default to render queue 3000. ([Change the sorting order, 6000.3](https://docs.unity.com/en-us/engine/6000.3/manual/unity2d/sprite/sort-sprites/2d-renderer-sorting))
- **The 2D renderer's own grouping.** `LayerUtility.CalculateBatches` walks the sorting layers and merges each run of layers that "share the same set of lights and shadows" into a `LayerBatch` with a `SortingLayerRange`. ([LayerUtility.cs#L122](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Runtime/2D/Passes/Utility/LayerUtility.cs#L122)) Each is drawn with `SortingCriteria.CommonTransparent`. ([DrawRenderer2DPass.cs#L132](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Runtime/2D/Rendergraph/DrawRenderer2DPass.cs#L132)) The merging of sprites into draws happens inside that engine call.
- **Atlases and the SRP Batcher.** "A sprite atlas combines multiple textures into a single texture. Unity only needs to create one draw call for all the sprites in a sprite atlas." But "If you use the Scriptable Render Pipeline Batcher, the number of draw calls might not decrease, but performance still improves a similar amount." ([Sprite atlases, 6000.5](https://docs.unity.com/en-us/engine/6000.5/manual/unity2d/sprite/atlas/atlas-introduction)) That fits the source: sprite colour lives in `UnityPerDraw`, which the SRP Batcher binds per object.
- **Dynamic batching.** It "Transforms mesh vertices into world space on the CPU", is "no longer recommended" for most uses, takes meshes of at most 300 vertices or 900 attributes, and "Batching of transparent GameObjects might be limited because Unity sorts all meshes back-to-front before batching." The page does not mention sprites. ([Introduction to batching meshes, 6000.3](https://docs.unity.com/en-us/engine/6000.3/manual/analysis/graphics-performance-profiling/reduce-draw-calls/draw-call-batching/draw-call-batching))

### Godot

- **Layers and z.** A `CanvasLayer`'s index "defines the draw order", and "This order will hold regardless of the CanvasItem.z_index of the nodes within each layer". Each layer is drawn on one viewport. ([CanvasLayer.xml#L7](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CanvasLayer.xml#L7)) `z_index` is relative to the parent by default (`z_as_relative`). With `y_sort_enabled`, children "with a higher Y position are rendered in front", and "Nodes sort relative to each other only if they are on the same z_index". ([CanvasItem.xml#L702–L714](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CanvasItem.xml#L702)) The culler clamps z to `CANVAS_ITEM_Z_MIN…MAX` (−4096…4096) and appends each item to its z bucket in traversal order. ([renderer_canvas_cull.cpp#L433](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_canvas_cull.cpp#L433), [rendering_server_enums.h#L40](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/rendering_server_enums.h#L40)) Y-sort ties fall back to `ysort_index`, the tree order. ([renderer_canvas_cull.h#L117](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_canvas_cull.h#L117))
- **Batch breaks.** In `_render_batch_items`: a new clip owner or a new material starts a batch. ([renderer_canvas_render_rd.cpp#L2201](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L2201), [#L2223](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L2223)) In `_record_item_commands`: lighting turning on or off, a different command type, LCD blending, a change of MSDF range or outline, a different texture state (texture, filter, repeat), and "Mesh's can't be batched, so always create a new batch". ([#L2395](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L2395), [#L2411–L2466](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L2411), [#L2745](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L2745)) A full instance buffer flushes and starts another. ([#L3291](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L3291)) Clipping is a scissor rectangle per batch. Its size is `item_buffer_size`, 16384 by default, and `uniform_set_cache_size` (4096) caches texture sets "if the project renders many unique sprite textures every frame". ([ProjectSettings.xml#L2827](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/ProjectSettings.xml#L2827))
- **Atlases.** `AtlasTexture` draws a region of another texture, and "Packing many smaller textures into a singular large texture helps to optimize video memory costs and render calls". ([AtlasTexture.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/AtlasTexture.xml#L7)) There is no runtime auto-atlas for sprites, only the font caches.

### Bevy

- **Sort.** A transparent `Mesh2d` goes into `Transparent2d` with `sort_key: FloatOrd(mesh_z + depth_bias)`. ([material.rs#L1191](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/material.rs#L1191)) The phase sorts by that key. ([core_2d/mod.rs#L360](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_core_pipeline/src/core_2d/mod.rs#L360)) Opaque and alpha-masked meshes are binned instead, by pipeline, draw function, mesh asset and material bind group, and drawn against a depth buffer. ([material.rs#L1123](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/material.rs#L1123)) There are no layers or Y-sort: a game writes `z`.
- **Batching.** Consecutive sorted items merge when `get_batch_data` returns equal compare data: the mesh asset and the material's bind group. `NoAutomaticBatching` opts an entity out. ([mesh.rs#L500–L529](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/mesh2d/mesh.rs#L500)) The instanced text pipeline merges successive glyph sprites of one image, and "If there is a phase item that is not a sprite, then we must start a new batch … to respect draw order". Each batch is one `draw_indexed(0..6, 0, range)`. ([render/mod.rs#L606–L615](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/render/mod.rs#L606), [#L832](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/render/mod.rs#L832))
- **Atlases.** `TextureAtlasLayout` is a size and a list of `URect`s over one image, and `TextureAtlas` is a layout handle and an index. ([texture_atlas.rs#L104](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_image/src/texture_atlas.rs#L104), [#L214](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_image/src/texture_atlas.rs#L214)) `TextureAtlasBuilder` packs images into one atlas with `rectangle_pack`, on request, not automatically. ([texture_atlas_builder.rs#L39](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_image/src/texture_atlas_builder.rs#L39))

### MonoGame and raylib

- **MonoGame.** `Deferred` draws "in order of draw call sequence", `Texture` sorts by texture, and `BackToFront` and `FrontToBack` sort by depth with "An unstable sort … sprites with equal depth may not have their order preserved". ([SpriteSortMode.cs](https://github.com/MonoGame/MonoGame/blob/76ed1c24f7dbe91421023c553978fa723548b22a/MonoGame.Framework/Graphics/SpriteSortMode.cs#L10)) `DrawBatch` flushes when `!ReferenceEquals(item.Texture, tex)`, in groups of at most `short.MaxValue / 6` quads. ([SpriteBatcher.cs#L30](https://github.com/MonoGame/MonoGame/blob/76ed1c24f7dbe91421023c553978fa723548b22a/MonoGame.Framework/Graphics/SpriteBatcher.cs#L30), [#L204](https://github.com/MonoGame/MonoGame/blob/76ed1c24f7dbe91421023c553978fa723548b22a/MonoGame.Framework/Graphics/SpriteBatcher.cs#L204))
- **raylib.** `rlSetTexture` starts a new draw entry when the texture changes. `rlSetShader` and `rlSetBlendMode` flush the batch on change, and `BeginMode2D` and `BeginScissorMode` flush before changing the matrix or scissor. ([rlgl.h#L1638](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rlgl.h#L1638), [#L2118](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rlgl.h#L2118), [#L4592](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rlgl.h#L4592), [rcore.c#L930](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rcore.c#L930), [#L1084](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rcore.c#L1084)) The defaults are 8192 quads and 256 draw calls a batch. ([rlgl.h#L49](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rlgl.h#L49)) `SetShaderValueV` writes the uniform at once and does not flush. ([rcore.c#L1370](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rcore.c#L1370)) So a uniform changed between two draws of one batch reaches both: a per-draw value must go through the vertex colour or an explicit flush.

## 5. The 2D camera

| | Unity URP 2D | Godot 4.7 | Bevy 0.20 | MonoGame | raylib |
|---|---|---|---|---|---|
| **Projection** | a `Camera` in orthographic mode; `orthographicSize` is the half-height | `Camera2D` sets the viewport's canvas transform | `Camera2d` requires an `OrthographicProjection` (`near` −1000, `far` 1000) | `transformMatrix` × an ortho over the viewport in pixels | `Camera2D{offset, target, rotation, zoom}` as a model-view matrix |
| **Zoom** | change `orthographicSize` | `zoom` (`Vector2`) | `scale` | in the matrix | `zoom` |
| **Logical resolution** | Pixel Perfect Camera's reference resolution and pixels per unit | stretch mode `disabled`, `canvas_items` or `viewport`, aspect `ignore`, `keep`, `keep_width`, `keep_height` or `expand`, scale mode `fractional` or `integer` | `ScalingMode`: `WindowSize`, `Fixed`, `AutoMin`, `AutoMax`, `FixedVertical`, `FixedHorizontal`, and `viewport_origin` as the pivot | none | none |
| **Pixel-perfect** | crop frame (none, pillarbox, letterbox, windowbox, stretch fill), grid snapping (none, pixel snapping, upscale render texture), filter (Retro AA, point) | `snap_2d_transforms_to_pixel`, `snap_2d_vertices_to_pixel`, integer scale | none: the `pixel_grid_snap` example | none | none |
| **Several cameras** | Base cameras with viewport rects; Overlay cameras stacked (the 2D renderer allows both) | one active camera per viewport; more viewports via `SubViewport`; `CanvasLayer`s outside the camera | any number, with `viewport`, `order`, `RenderLayers` and an image `RenderTarget` | one matrix per `Begin` | one per `BeginMode2D` |

- **Unity.** `orthographicSize` is the "Camera's half-size when in orthographic mode". ([Camera.orthographicSize](https://docs.unity.com/en-us/engine/current/script-reference/unityengine/camera/orthographicsize)) The Pixel Perfect Camera's enums, from its source: `CropFrame` `None`, `Pillarbox`, `Letterbox`, `Windowbox`, `StretchFill`. `GridSnapping` `None`, `PixelSnapping` ("make Sprites appear to move in pixel-by-pixel increments"), and `UpscaleRenderTexture` ("rendered to a temporary texture set as close as possible to the Reference Resolution … then upscaled to fit the full screen"). `PixelPerfectFilterMode` `RetroAA` (point to the closest multiple, then bilinear) and `Point`. ([PixelPerfectCamera.cs#L20–L76](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Runtime/2D/PixelPerfectCamera.cs#L20), [reference, 6000.3](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/2d-pixelperfect-ref.html)) The 2D renderer returns Base and Overlay from `SupportedCameraStackingTypes`. ([Renderer2DRendergraph.cs#L120](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Runtime/2D/Rendergraph/Renderer2DRendergraph.cs#L120)) Split screen is several Base cameras with viewport rects. ([split-screen in URP, 6000.0](https://docs.unity.com/en-us/engine/6000.0/manual/cameras/urp/multiple/rendering-to-the-same-render-target))
- **Godot.** `Camera2D` "forces the screen (current layer) to scroll following this node", and "Only one camera can be active per viewport". A custom camera sets `Viewport.canvas_transform` itself. ([Camera2D.xml#L7–L11](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/Camera2D.xml#L7)) Its other members are anchor mode, offset, drag margins, limits, position and rotation smoothing, and `ignore_rotation`, which is true by default. The `zoom` note says rasterised fonts blur when zoomed and recommends MSDF. ([#L189](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/Camera2D.xml#L189)) The stretch settings are in `display/window/stretch/*`. `canvas_items` and `expand` are "the default for projects created starting in Godot 4.7", and `integer` scale makes "the screen size … always be an integer multiple of the base viewport size". ([ProjectSettings.xml#L1079–L1099](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/ProjectSettings.xml#L1079)) The snap settings "snap to full pixels … at the cost of less smooth movement". ([#L2847–L2856](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/ProjectSettings.xml#L2847)) The shader honours it with `canvas_data.use_pixel_snap`. ([canvas.glsl#L289](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas.glsl#L289))
- **Bevy.** `Camera2d` requires `Projection::Orthographic(OrthographicProjection::default_2d())`, whose `near` is −1000. ([components.rs#L8–L16](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_camera/src/components.rs#L8), [projection.rs#L771](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_camera/src/projection.rs#L771)) The `ScalingMode` variants are documented one by one, and "zooming should be done by changing `OrthographicProjection::scale`, rather than changing the parameters of the scaling mode". ([projection.rs#L523–L613](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_camera/src/projection.rs#L523)) "Cameras with a higher order are rendered later, and thus on top of lower order cameras", and `viewport` limits a camera to a rectangle of its target. ([camera.rs#L385](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_camera/src/camera.rs#L385)) `pixel_grid_snap` renders layer 0 into a 160×90 image and draws it, upscaled, with a second camera that sees layer 1. ([pixel_grid_snap.rs](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/examples/2d/pixel_grid_snap.rs#L1))
- **MonoGame and raylib.** `SpriteEffect` builds `CreateOrthographicOffCenter(0, vp.Width, vp.Height, 0, 0, -1)` and multiplies `TransformMatrix` in front of it. ([SpriteEffect.cs#L71–L83](https://github.com/MonoGame/MonoGame/blob/76ed1c24f7dbe91421023c553978fa723548b22a/MonoGame.Framework/Graphics/Effect/SpriteEffect.cs#L71)) raylib's `GetCameraMatrix2D` is translate(−target) × scale(zoom) × rotate × translate(offset). ([rcore.c#L1479](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/rcore.c#L1479), [raylib.h#L338](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/src/raylib.h#L338))

## 6. Outline, glow and dissolve

| | Sprite outline | Text outline | Glow | Dissolve |
|---|---|---|---|---|
| **Unity** | a material (Shader Graph) | TextMesh Pro SDF material: Outline, Underlay, Glow | URP bloom on HDR; 2D lights | a material |
| **Godot** | a `ShaderMaterial` | `Label` `outline_size`, stacked outlines and shadows: separate runs of glyph draws, outlines first | `Environment` glow with HDR 2D | a `ShaderMaterial` |
| **Bevy** | a `SpriteMaterial` extension | none; `Text2dShadow` draws extra glyph sprites | `Bloom` on a `Camera2d` | a `SpriteMaterial` extension or `Material2d` |
| **raylib** | a fragment shader (`shaders_texture_outline`) | the SDF example's shader | — | a shader |

- **A fragment outline stays inside the quad.** raylib's `outline.fs` samples the alpha at four diagonal offsets of `outlineSize / textureSize` and mixes `outlineColor` under the texel. ([outline.fs](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/examples/shaders/resources/shaders/glsl330/outline.fs), [shaders_texture_outline.c](https://github.com/raysan5/raylib/blob/bcb85817b5d3da2594ff138df90e1faddb73b8f6/examples/shaders/shaders_texture_outline.c#L43)) Its outline can only land where the quad already covers transparent texels. To reach past the frame, a material needs the vertex stage. Bevy's sprite material has `vertex_scale` and `vertex_offset` in its uniform, applied to the unit quad in the vertex shader. ([sprite_material.wesl](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/sprite_mesh/sprite_material.wesl)) Godot's `vertex()` may move `VERTEX`. On an atlas, neighbouring samples read the next sprite unless there is padding: Unity's atlas pads 4 pixels by default. ([Sprite Atlas reference, 6000.1](https://docs.unity3d.com/6000.1/Documentation/Manual/sprite/atlas/sprite-atlas-reference.html))
- **Godot's text effects are a feature, drawn as runs.** Per line, `Label` draws shadow outline, shadow, stacked shadows, stacked outlines, outline, then text, each over all glyphs: "Do not merge this into the single loop iteration, to prevent overlaps". ([label.cpp#L842–L901](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/gui/label.cpp#L842)) It warns when the MSDF pixel range is too small for the outlines. ([#L712](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/gui/label.cpp#L712)) With MSDF, the outline width is batch state, so the outline run and the fill run are different batches. ([renderer_canvas_render_rd.cpp#L2451](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L2451)) All of it stays inside the one canvas item's slot in the order.
- **TextMesh Pro.** The Distance Field shader's groups are Face, Outline ("Adds a colored and/or textured outline"), Underlay ("Adds a second rendering of the text underneath the original rendering, for example to add a drop shadow"), Glow ("Adds a smooth outline to the text in order to simulate glow") and Lighting. ([Distance Field shaders, uGUI 2.0](https://docs.unity3d.com/Packages/com.unity.ugui@2.0/manual/TextMeshPro/ShadersDistanceField.html))
- **Glow.** Godot's HDR 2D "allows 2D rendering to take advantage of effects requiring high dynamic range (e.g. 2D glow)". ([ProjectSettings.xml#L3511](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/ProjectSettings.xml#L3511)) Bevy's `bloom_2d` puts `Bloom::default()` and a tonemapper on a `Camera2d`. ([bloom_2d.rs#L24](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/examples/2d/bloom_2d.rs#L24))
- **Group effects.** Godot's `CanvasGroup` "Merges several 2D nodes into a single draw operation" through the backbuffer, and a material on it replaces its built-in shader. That is the way to outline or fade a composite as one. ([CanvasGroup.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CanvasGroup.xml#L4))

## 7. What bears on cog: WebGPU, render and v1

- **No push constants.** Godot's canvas renderer puts per-batch state (specialisation bits, MSDF range, texture pixel size) and, for meshes, the whole transform and modulate in a push constant. ([canvas_uniforms_inc.glsl#L51](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/canvas_uniforms_inc.glsl#L51)) WebGPU has none. render's equivalent is a `@group(2)` draw parameter, a uniform block at a dynamic offset ([render design](../../../render/docs/design.md)). Bevy's 2D path needs no push constants: its rows sit in a storage array read at `instance_index`, the shape render already offers.
- **No bindless.** Bevy's bindless needs `TEXTURE_BINDING_ARRAY` (and `BUFFER_BINDING_ARRAY` for buffer arrays), which WebGPU does not have. ([as_bind_group.rs#L978–L999](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/macros/src/as_bind_group.rs#L978)) Without it, each `SpriteMeshMaterial` is its own bind group, and the batch compare data includes the bind group. So two sprites that differ in tint, flip or rectangle cannot share a draw. That is an inference from the source, not a measurement. Bevy's sprite design leans on bindless, and the older per-instance colour, which batched without it, is what Bevy 0.20 dropped for sprites.
- **Instance data: vertex attributes or storage.** Godot uses 8 instance-rate attribute locations (8–15) for its record, and Bevy's text pipeline uses 5. WebGPU's defaults allow 16 attributes and 8 vertex buffers. render offers both paths (design, user story 42). Storage at `instance_index` has no attribute budget and lets a user's shader read a wider record. render's per-instance storage buffer is a `@group(2)` draw parameter, at most 4 storage buffers per pipeline there.
- **Texture changes break every engine's batch.** Each engine above starts a draw on a new texture, and Unity's and Godot's docs present atlases as the remedy. render's atlas page is a layer of a 2D-array texture (map #860's notes), so sprites on different pages can share one binding, the layer carried per instance, as v1's canvas did.
- **The per-sprite record and v1's frozen 96 bytes.** No engine lets a user add a member to its sprite record. All three big engines answer with one small per-instance value that indexes or encodes user data: RSUV (32 bits), `MeshTag` (`u32`) with `GpuComponentArrayBuffer`, and `instance uniform` offsets. Bevy and Godot store the indirection beside the record, so it costs no batch. v1's lesson was "no API to add a per-sprite member" ([v1 findings §4](../../../render/docs/research/v1-renderers.md)).
- **A material keyed by values.** Bevy's sprite material cache is keyed by every sprite value, colour included, and evicts when unheld. ([sprite_mesh/mod.rs#L84–L159](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_sprite_render/src/sprite_mesh/mod.rs#L84)) That is the shape v1's canvas warned against: "a material rebuilt each frame at a changing value is a new set every frame". Bevy at least releases a material when no entity holds it.
- **Clip.** Godot clips with a scissor per batch, so a new clip owner breaks the batch. ([renderer_canvas_render_rd.cpp#L2201](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/renderer_canvas_render_rd.cpp#L2201)) v1 clipped with a discard that any custom fragment shader could skip.
- **Halo and painter's order.** Godot draws text outlines as a run before the fill run, inside one item's slot in the order. v1's halo used two layers, which clashed with painter's-order sorting in a game ([#188](https://github.com/dvoyni/cog/issues/188)).

## 8. Not verified

- **Unity's sprite batching.** The merging of sprites into draws, SRP or dynamic, is in Unity's closed core. The official pages read do not say how `SpriteRenderer`s batch under the 2D renderer. A forum answer (2025-08-22, by "Venkify", whom the asker calls Unity staff; the page shows no badge) says the 2D renderers are SRP-batched when the shader is compatible, that the 2D path "avoids using MaterialPropertyBlock" as "a special-case for 2D Renderers", and that "TexelSize/Offset are still not supported for SRP-Batcher when using 2D Renderers" (2026-11-06). ([thread](https://discussions.unity.com/t/need-clarifications-about-srp-batcher-2d-urp-and-spriterenderer/1680153)) A Unity issue-tracker entry, seen only as a search snippet, dates SRP batching for 2D renderers to 2023.1.0a18. Neither is first-party documentation.
- **Which path carries Unity's sprite colour.** The vertex colour, `unity_SpriteColor` in `UnityPerDraw` and the instanced array are all in the shader. Which one the engine fills in each batching mode is inferred from the source comment, not documented.
- **TextMesh Pro's passes.** The page does not say whether the underlay and glow are drawn in the fill's pass or in another one. TextMesh Pro's shader source was not read.
- **Bevy's batching on WebGPU.** That differently-tinted sprites each draw alone without bindless follows from the source (compare data includes the material bind group, and bindless needs a native-only feature). It was not measured, and the 0.20 notes claim "improved performance in many cases" without naming backends.
- **Bevy's sort stability.** `Transparent2d::sort` uses `IndexMap::sort_by_key`. Whether equal `z` keeps insertion order was not checked, and insertion order is not a user-facing order in any case.
- **Godot's push constant on WebGPU.** Godot's web export uses the Compatibility (GLES3) renderer, not this RenderingDevice path, so how its canvas would map to WebGPU is not shown by its code.
- **Versions.** Unity's manual pages span 6000.0 to 6000.6, and the URP source is `master`. A detail that changed between those versions may be cited from a newer page than a shipped Unity 6 LTS has.

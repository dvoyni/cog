# Frame structure: URP, Bevy, Godot and Frostbite

Research for [#803](https://github.com/dvoyni/cog/issues/803), on the map [#800](https://github.com/dvoyni/cog/issues/800). It asks how four renderers that sit where draw will sit shape their API and their frame: passes and transient targets, how draws are gathered and batched, how per-object and per-material data reach shaders, what a material is, and what the handles a user holds are. It records facts and decides nothing for draw. The last section notes what is specific to WebGPU and to our wgpu fork.

## In short

- **The frame graph is declared in URP and Frostbite, and absent in Bevy and Godot.** URP's render graph and Frostbite's FrameGraph have each pass declare what it creates, reads and writes, then cull unused passes and give transient textures lifetimes. Bevy 0.19 deleted its render graph, so passes are now plain ECS systems ordered by system sets. Godot gives fixed hook points in a fixed pipeline, and its `RenderingDeviceGraph` reorders commands and solves barriers below the API.
- **Transient targets are reused, but only Frostbite aliases memory.** URP and Bevy reuse whole textures by descriptor. URP reuses one inside a frame after its last reader. Bevy holds each for the whole frame. Frostbite places transient resources in shared memory (147 MB → 80 MB at 720p on DX12). Godot keeps named textures per viewport.
- **Batching groups by what the GPU must rebind.** URP's SRP Batcher keeps per-material constants resident and groups draws by shader variant. Bevy bins by pipeline, material bind group and mesh slab, then draws each mesh bin as one instance range, multi-drawn per batch set. Godot sorts on a 128-bit key and merges runs of equal keys into one instanced draw.
- **Per-object data is a big buffer indexed per instance.** URP uses one large per-object constant buffer. Bevy uses a storage buffer `array<Mesh>` indexed by `instance_index`, falling back to a uniform array at a dynamic offset. Godot uses a storage buffer indexed by a push-constant base plus `gl_InstanceIndex`. Bevy reaches the row without push constants, because a direct draw's first instance is the row.
- **A material is a shader plus a parameter block plus a key.** The key picks a variant. Bevy and Godot cache pipelines by a compact key (with the vertex layout and pass), not by the whole descriptor. Bevy's `PipelineCache` says outright that it does not deduplicate identical descriptors. URP's PSO caching is engine-internal.
- **Handles:** URP gives managed object references, and its render graph handles are index, version and execution stamp. Bevy gives `Handle<T>` (strong `Arc` or UUID) and `AssetId` (index and generation). Godot gives a 64-bit `RID` (validator and index) owned by a ref-counted `Resource`. Frostbite's setup handles live for one frame.

## 1. Passes, render targets and post effects

| | Unity URP | Bevy 0.20 | Godot 4.7 | Frostbite FrameGraph |
|---|---|---|---|---|
| **To add a pass, a user declares** | a `ScriptableRenderPass` whose `RecordRenderGraph` adds raster, compute or unsafe graph passes, enqueued each frame per camera by a `ScriptableRendererFeature` | a system in a camera schedule (`Core3d`, `Core2d`) in a system set, taking `RenderContext` and `ViewQuery` | a `CompositorEffect` resource with a callback type and `_render_callback`, in a `Compositor` on a `WorldEnvironment` or `Camera3D` | `addCallbackPass<PassData>(name, setup, execute)`, or a class per pass |
| **Ordering** | `renderPassEvent` (`BeforeRendering` = 0 … `AfterRendering` = 1000); graph passes run in declaration order | system sets `Prepass → MainPass → EarlyPostProcess → PostProcess`, chained weakly, plus `.before`/`.after` | five fixed points: pre-opaque, post-opaque, post-sky, pre-transparent, post-transparent | the graph, rebuilt every frame from code |
| **Inputs and outputs** | builder calls: `UseTexture(h, AccessFlags)`, `SetRenderAttachment`, `UseRendererList`; frame textures from `UniversalResourceData` | none declared; textures live on view entities (`ViewTarget`, depth, prepass textures) | `RenderSceneBuffersRD` by context and name, `get_color_layer(view)`; flags ask the renderer for motion vectors, normal-roughness, MSAA resolves | `builder.read`, `builder.write` (a write versions the resource), `builder.createTexture`, `useRenderTarget`; a blackboard between modules |
| **A target that outlives the frame** | an `RTHandle` made outside the graph and `ImportTexture`d; the graph tracks it, not its lifetime | a camera's `RenderTarget::Image(handle)`, `TextureView` or `None` | a `SubViewport` shown through a `ViewportTexture` | imported external resources (TAA history, back buffer) |
| **A post effect** | a renderer feature plus a `VolumeComponent` read from `VolumeManager.instance.stack`; blit to a new texture and set `resourceData.cameraColor` to it | a camera component, extracted, its uniform at a dynamic offset, and a system calling `ViewTarget::post_process_write()` (ping-pong); packaged as `FullscreenMaterial` | a `CompositorEffect` at post-transparent, before the built-in post effects | a render module: a free function over graph handles, or a persistent module owning its history |
| **Transient targets made by** | `renderGraph.CreateTexture(desc)`; `builder.CreateTransientTexture` for one pass | `TextureCache::get(device, descriptor)` in a prepare system | `create_texture(context, name, …)`, which returns the existing texture if it exists | `builder.createTexture(desc)` in setup, its size and format derivable from inputs |
| **Pooling** | `TexturePool` keyed by the descriptor's hash; purged after 10 frames unused | `HashMap<TextureDescriptor, Vec<…>>`; dropped after 3 frames unused | per viewport, kept until reconfigured; the cross-viewport sharing flag is a TODO | per-platform back end: object pools, texture memory pools, a linear allocator for buffers |
| **Reuse within a frame** | yes, after the last reader ("intra-frame memory aliasing", on unless the Frame Debugger is open) | no: a texture is taken until the end-of-frame cleanup | no | yes: acquired just before first use, released after last use |
| **Memory aliasing** | none in the pool source: only whole textures of an equal descriptor are reused | none | none at this level; RD's `TEXTURE_USAGE_TRANSIENT_BIT` is not yet used for scene buffers | physical or virtual aliasing on PS4, Xbox One and DX12, with discard or clear and aliasing barriers |
| **Unused passes** | culled unless `AllowPassCulling(false)` | not culled; a system is skipped when the current view lacks its `ViewQuery` components | n/a | culled with their unreferenced resources |

### Unity URP

- **Pass.** Declare a class deriving from `ScriptableRenderPass` and override `RecordRenderGraph(RenderGraph renderGraph, ContextContainer frameContext)`. That method declares inputs and outputs and records no commands. Inside it, `renderGraph.AddRasterRenderPass<PassData>(name, out passData)` returns a builder. The render function is `builder.SetRenderFunc(static (PassData data, RasterGraphContext context) => …)`. A Scriptable Renderer Feature's `Create` makes the pass and sets `renderPassEvent`, and `AddRenderPasses(renderer, ref renderingData)` calls `renderer.EnqueuePass`, "every frame, once for each Camera". ([write a render pass](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/render-graph-write-render-pass.html), [inject a pass](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/renderer-features/scriptable-renderer-features/inject-a-pass-using-a-scriptable-renderer-feature.html), [`RecordRenderGraph`](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Runtime/Passes/ScriptableRenderPass.cs#L311))
- **Injection points.** The `RenderPassEvent` values, in order: `BeforeRendering` 0, shadows 50/100, prepasses 150/200, G-buffer 210/220, deferred lights 230/240, opaques 250/300, skybox 350/400, transparents 450/500, post-processing 550/600, `AfterRendering` 1000. ([`RenderPassEvent`](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Runtime/Passes/ScriptableRenderPass.cs#L67))
- **Graph API.** `CreateTexture(in TextureDesc)`, `ImportTexture(RTHandle)`, `ImportBackbuffer`, `CreateBuffer`, `CreateRendererList`, and `AddRasterRenderPass`, `AddComputePass` and `AddUnsafePass`. The builder has `UseTexture(in TextureHandle, AccessFlags)`, `CreateTransientTexture` ("only be available for the current pass"), `UseRendererList`, `EnableAsyncCompute`, `AllowPassCulling` and `AllowGlobalStateModification`. ([RenderGraph.cs#L594–L1406](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/RenderGraph.cs#L799), [IRenderGraphBuilder.cs](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/IRenderGraphBuilder.cs#L70))
- **Phases.** Setup declares the passes and their resources. Compilation culls the passes whose outputs no other pass uses, and computes lifetimes and async-compute sync points. Execution runs the rest in declaration order. "There is no persistence between each execution of a render graph." A resource is allocated just before its first writer and released after its last reader. On tile-based GPUs, passes merge into one native render pass (`nativeRenderPassesEnabled`, default true). The compiled graph can be cached by hashing the graph's structure. ([fundamentals, SRP Core 17.0.4](https://docs.unity3d.com/Packages/com.unity.render-pipelines.core@17.0/manual/render-graph-fundamentals.html), [introduction](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/render-graph-introduction.html), [RenderGraph.cs#L361](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/RenderGraph.cs#L361), [#L1552](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/RenderGraph.cs#L1552))
- **Pool.** Released textures go back into `m_ResourcePool`, keyed by the descriptor hash. `TryGetResource` takes the most recent entry. With intra-frame aliasing off, it takes only entries released in an earlier frame or execution. Aliasing is on except when the Frame Debugger is enabled, under checks. `PurgeUnusedResources` releases entries unused for `kStaleResourceLifetime = 10` frames; the comment says this keeps off-screen cameras from reallocating each frame. ([RenderGraphResourcePool.cs#L15–L100](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/RenderGraphResourcePool.cs#L65), [#L197](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/RenderGraphResourcePool.cs#L197), [RenderGraph.cs#L1475](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/RenderGraph.cs#L1475))
- **Frame textures.** `UniversalResourceData` holds `activeColorTexture` ("To be referenced at RenderGraph pass recording time"), `backBufferColor`, `cameraColor` and `cameraDepth` (both settable), `gBuffer[]`, `cameraDepthTexture` and `cameraNormalsTexture`. A pass that blits into a new texture can assign `resourceData.cameraColor = destination` instead of blitting back. ([UniversalResourceData.cs#L126](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.universal/Runtime/FrameData/UniversalResourceData.cs#L126), [blit](https://docs.unity3d.com/6000.3/Documentation/Manual/urp/render-graph-blit.html))
- **Post effect.** The editor template makes two scripts: a Renderer Feature, with its pass and material, and a Volume component. `AddRenderPasses` reads `VolumeManager.instance.stack?.GetComponent<T>()` and skips the pass when the component is inactive. ([custom post-processing with Volume, 6000.3](https://docs.unity.com/en-us/engine/6000.3/manual/post-processing-and-full-screen-effects/urp/custom-post-processing/with-volume))

### Bevy

- **No render graph since 0.19.** PR [#22144](https://github.com/bevyengine/bevy/pull/22144), merged 2026-01-28, "removes the `RenderGraph` in favor of using systems". Its reasons: the graph's slot system for resources "has never been used", and `Schedule` had become "co-extensive" with it. It lists resource management "in ECS terms" as future work. The release notes say "Render passes are now regular systems". ([0.19 notes](https://bevy.org/news/bevy-0-19/))
- **Shape.** The render sub-app's `RenderSystems` run in this order: `ExtractCommands`, `PrepareAssets`, `PrepareMeshes`, `CreateViews`, `Specialize`, `PrepareViews`, `Queue` (with `QueueMeshes` and `QueueSweep`), `PhaseSort`, `Prepare` (resources, batching phases, writing phase buffers, flush, bind groups), `Render`, `Cleanup` and `PostCleanup`. ([lib.rs#L186](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/lib.rs#L186)) In `Render`, `render_system` runs the root schedule, still named `RenderGraph`. There `camera_driver` runs each camera's schedule, plus the shadow views not tied to a camera, with `CurrentView` set. ([renderer/mod.rs#L94](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/renderer/mod.rs#L94), [schedule.rs#L136](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_core_pipeline/src/schedule.rs#L136)) `Core3dSystems` is `Prepass, MainPass, EarlyPostProcess, PostProcess`, chained weakly ([#L50](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_core_pipeline/src/schedule.rs#L50)). The render app runs between main-schedule iterations, or in parallel with the next one under `PipelinedRenderingPlugin`. ([lib.rs#L151](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/lib.rs#L151))
- **Post effect, by hand.** The `custom_post_processing` example adds `prepare_bind_groups` in `RenderSystems::PrepareBindGroups` and `post_process_system.in_set(Core3dSystems::PostProcess)` to `Core3d`. The system's `ViewQuery<(&ViewTarget, &DynamicUniformIndex<Settings>, &BindGroups)>` skips views without the effect. ([example](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/examples/shader_advanced/custom_post_processing.rs#L63)) `ViewTarget::post_process_write()` flips between two main textures, `a` and `b`, and the caller "_must_ ensure `source` is copied to `destination`". ([view/mod.rs#L1034](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/view/mod.rs#L1034))
- **Post effect, packaged.** `FullscreenMaterial` is a camera component with a uniform layout and `fragment_shader()`. By default it runs in `Core3dSystems::PostProcess` before `tonemapping`, and its pipeline is specialised by target format. ([fullscreen_material.rs#L80](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_core_pipeline/src/fullscreen_material.rs#L80)) Built-in effects are camera components such as `Vignette` and `LensDistortion`. ([0.19 notes](https://bevy.org/news/bevy-0-19/))
- **Transient textures.** `TextureCache` maps each `TextureDescriptor` to a list. `get` returns an entry not yet `taken` that frame, or creates one. `update`, in `RenderSystems::Cleanup`, clears `taken` and drops entries unused for 3 frames. Two passes that ask for one descriptor in a frame therefore get two textures. ([texture_cache.rs#L31](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/texture/texture_cache.rs#L31), [#L92](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/texture/texture_cache.rs#L92), [texture/mod.rs#L42](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/texture/mod.rs#L42))
- **Render targets.** A camera's `RenderTarget` is `Window`, `Image`, `TextureView` (made outside Bevy, for OpenXR for example) or `None`, which renders prepasses only. ([camera.rs#L893](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_camera/src/camera.rs#L893))

### Godot

- **CompositorEffect** is marked experimental. It is an abstract `Resource` with `effect_callback_type`, `enabled`, `access_resolved_color`/`_depth`, `needs_motion_vectors` and `needs_normal_roughness`. `_render_callback(effect_callback_type, render_data)` "happens on the rendering thread", and `render_data` "should not be stored". The five callback types are listed in the table. ([CompositorEffect.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/CompositorEffect.xml#L77)) The manual's example dispatches compute on the color layer with `UniformSetCacheRD.get_cache(shader, 0, [uniform])`. It works only in Forward+ and Mobile, and in 3D only. ([The Compositor](https://docs.godotengine.org/en/stable/tutorials/rendering/compositor.html))
- **Scene buffers.** One `RenderSceneBuffersRD` exists per viewport with 3D. Its buffers sit in contexts, with `render_buffers` as the default. "Buffers are only guaranteed to exist during rendering of the viewport." `create_texture(context, name, format, usage, samples, size, layers, mipmaps, unique, discardable)` "will return the existing texture if it already exists". ([RenderSceneBuffersRD.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/RenderSceneBuffersRD.xml)) For `unique`, the source says: "TODO … this is a texture that can be shared. This will be implemented later as an optimization." ([render_scene_buffers_rd.cpp#L329](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/storage_rd/render_scene_buffers_rd.cpp#L329)) `is_discardable` tells the RenderingDevice (RD) it need not keep the contents between frames ([RDTextureFormat.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/RDTextureFormat.xml#L40)). The tile-memory `TEXTURE_USAGE_TRANSIENT_BIT` exists, but scene buffers do not use it yet (a TODO, [#L188](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/storage_rd/render_scene_buffers_rd.cpp#L188); [rendering_device_commons.h#L428](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/rendering_device_commons.h#L428)).
- **The graph beneath.** Since 4.3 ([PR #84976](https://github.com/godotengine/godot/pull/84976), merged 2024-01-09), RenderingDevice serialises every command into a `RenderingDeviceGraph`. The graph reorders commands "based on the dependency between the resources" and groups barriers into "levels". Draw lists now need only load, clear or discard and store or discard actions. The PR reports 60–80% fewer `vkCmdPipelineBarrier` calls and about 10% frame time on an RTX 3090 Ti. This is an automatic-barrier layer, not a pass-declaration API. ([rendering_device_graph.h#L49](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/rendering_device_graph.h#L49))
- **Render targets.** A `SubViewport` "must … be either put inside a [SubViewportContainer] or assigned to a [ViewportTexture]" to show anything. ([SubViewport.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/SubViewport.xml))

### Frostbite (FrameGraph, GDC 2017)

- **Why.** In 2007, Frostbite's WorldRenderer "orchestrates all rendering" through a code-driven architecture. It grew from about 4K to 15K lines, with single functions over 2K lines, and games forked it (slides 4–11). The goals were knowledge of the whole frame, decoupled modules, automatic resource management, and simpler async compute and barriers (slide 15).
- **Phases.** The design moves "away from immediate mode rendering" to a retained graph rebuilt every frame (slide 19). In setup, passes declare every resource they read, write or create, and external permanent resources are imported (slides 20–21). In compile, unreferenced passes and resources are culled, lifetimes computed, and memory acquired just before first use and released after last (slides 26–28). In execute, each pass's callback issues ordinary `RenderContext` commands, with handles resolved to real resources (slide 29).
- **Code.** A transient is declared as `FrameGraphTextureDesc desc; desc.width = 1280; desc.height = 720; desc.format = RenderFormat_D32_FLOAT; desc.initialSate = FrameGraphTextureDesc::Clear; m_renderTarget = builder.createTexture(desc);` (slide 22). Dependencies are `m_input = builder.read(input, readFlags); m_renderTarget = builder.write(renderTarget, writeFlags);`, and the diagram shows the write producing "Render Target (version 2)" (slide 23). A pass is `frameGraph.addCallbackPass<PassData>("MyRenderPass", [&](RenderPassBuilder& builder, PassData& data){ data.input = builder.read(input); data.output = builder.useRenderTarget(output).targetTextures[0]; }, [=](const PassData& data, const RenderPassResources& resources, IRenderContext* renderContext){ drawTexture2d(renderContext, resources.getTexture(data.input)); });` (slide 35). Async compute is opted into per pass with `builder.asyncComputeEnable(true)` (slide 33). `MoveSubresource` forwards one resource into another, for example faces into a cubemap (slides 24–25).
- **Modules.** Stateless free functions take and return graph handles. Persistent modules own lookup tables and history. A blackboard of typed components (`blackboard.add<BlurPyramidData>()` and `blackboard.get<…>()`) carries handles between modules. The WorldRenderer shrank from about 15K to 5K lines (slides 36–37).
- **Transient resources** last at most one frame (slide 39). The back end differs by platform: aliasing in physical or virtual memory, object pools, an atomic linear allocator for buffers, and texture memory pools (slide 40). DX12 suffers from fragmentation across many small heaps (slide 42). The first operation on aliased memory must be `DiscardResource` or a clear, preferably discard (slide 46). Aliasing barriers are needed and may serialise compute (slides 47–50). The results: at 720p, 147 MB without aliasing against 80 MB on DX12 PC, 77 MB on PS4 and 76 MB on Xbox One (32 MB ESRAM and 44 MB DRAM). At 4K on DX12, 1042 MB against 472 MB (slides 51–58).

## 2. Gathering, culling, sorting, batching, instancing, indirect

| | Unity URP | Bevy 0.20 | Godot 4.7 | Frostbite |
|---|---|---|---|---|
| **Where draws come from** | renderers culled by the engine into `CullingResults`; a pass turns them into a `RendererList` (shader pass tag, sorting, filtering) | entities with `Mesh3d` and `MeshMaterial3d<M>`, synced into a retained render world and extracted; queued per view into render phases | RenderingServer instances in a scenario (`instance_set_base`, `instance_set_scenario`), culled per camera into render lists | not in the FrameGraph talk; in 2007, "render blocks" queued by the user |
| **Culling** | engine-side CPU culling (see *Not verified*); the GPU Resident Drawer adds GPU occlusion culling; BatchRendererGroup (BRG) does none | CPU frustum culling in `CheckVisibility`; GPU frustum and two-phase occlusion culling in a compute pre-pass | `DynamicBVH` per scenario, culled on worker threads; an occlusion `HZBuffer` | 2016: per-cluster and per-triangle GPU culling in compute |
| **Sorting** | `SortingCriteria` flags; opaque: rough front-to-back and fewer state changes; transparent: back to front | binned phases (opaque): bin keys sorted, items unsorted within a bin; sorted phases (transparent): by view depth | opaque by a 128-bit state key; alpha by reverse depth and priority | 2007: "blocks are sorted (category & depth)" |
| **Batching unit** | SRP Batcher: one shader variant, whatever the material; fewer binds, not fewer draws | batch set = (pipeline, draw function, material bind group, mesh slabs, lightmap slab); bin = one mesh | a run of elements with equal sort keys | 2016: meshes sharing shader and vertex/index strides |
| **Instancing** | GPU Resident Drawer (automatic BRG), BRG, GPU instancing, `RenderMeshInstanced` | automatic: each bin is one instance range; manual through `NoIndirectDrawing` | automatic for equal-key runs (up to 2²⁰−1); `MultiMesh` explicitly | 2007: stream instancing |
| **Indirect** | `Graphics.RenderMeshIndirect` (args buffer; needs compute) | multi-draw indexed indirect per batch set, with a count buffer where supported, otherwise over the whole set with zeroed instance counts | only `MultiMesh` with `use_indirect` (GPU-writable instance count) | 2016: DX12 `ExecuteIndirect` with a count buffer, compacted by prefix sum |

### Unity URP

- **Renderer lists.** `new RendererListParams(renderingData.cullResults, drawSettings, filterSettings)`, then `renderGraph.CreateRendererList(...)`, `builder.UseRendererList(handle)`, and `context.cmd.DrawRendererList(handle)` in the render function. `RenderingUtils.CreateDrawingSettings(new ShaderTagId("UniversalForward"), …, sortFlags)` selects objects by their pass's `LightMode` tag. `FilteringSettings(RenderQueueRange.opaque, ~0)` selects by queue range; the page does not explain the second argument. `drawSettings.overrideMaterial` replaces the material. ([draw objects in a pass](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/render-graph-draw-objects-in-a-pass.html))
- **Sorting.** The flags are `SortingLayer`, `RenderQueue`, `BackToFront`, `QuantizedFrontToBack`, `OptimizeStateChanges`, `CanvasOrder` and `RendererPriority`. `CommonOpaque` is "typical sorting for opaque objects", with state-change optimisation and rough near-to-far order. `CommonTransparent` sorts far to near. ([SortingCriteria](https://docs.unity3d.com/6000.2/Documentation/ScriptReference/Rendering.SortingCriteria.html))
- **SRP Batcher.** It is "a draw call optimization" that "reduces render-state changes between draw calls". It batches by shader variant, not material. "All materials have persistent constant buffers located in GPU memory", and "dedicated code manages a large per-object GPU constant buffer for all per-object properties." ([SRP Batcher](https://docs.unity3d.com/6000.2/Documentation/Manual/SRPBatcher.html)) A batch is "a sequence of 'Bind', 'Draw', 'Bind', 'Draw'... GPU commands" ([Unity blog, A. Carré, 2019-02-28](https://unity.com/blog/engine-platform/srp-batcher-speed-up-your-rendering)).
- **Order of methods.** Each GameObject gets one method: SRP Batcher (with static batching) first, then GPU instancing (including the GPU Resident Drawer and BRG), then dynamic batching, which Unity no longer recommends. Unity advises disabling plain GPU instancing in URP to avoid extra shader variants. ([choose a method](https://docs.unity3d.com/6000.2/Documentation/Manual/optimizing-draw-calls-choose-method.html)) In URP, GPU instancing works with custom shaders "only if you disable the … SRP Batcher" or make the shader incompatible. ([GPU instancing](https://docs.unity3d.com/6000.2/Documentation/Manual/GPUInstancing.html))
- **GPU Resident Drawer** "automatically uses the BatchRendererGroup API to draw GameObjects with GPU instancing". It needs Forward+, compute shaders and Mesh Renderers, and is not available on OpenGL ES. Otherwise "Unity falls back to drawing the GameObject without GPU instancing". It has its own GPU occlusion culling. ([GPU Resident Drawer](https://docs.unity3d.com/6000.2/Documentation/Manual/urp/gpu-resident-drawer.html))
- **BatchRendererGroup.** The user calls `RegisterMesh` and `RegisterMaterial`, which return `BatchMeshID` and `BatchMaterialID`, then `AddBatch(metadata, graphicsBuffer)`, which returns a `BatchID`. A culling callback outputs draw commands and draw ranges with filter settings. BRG does no frustum or occlusion culling itself: "You must provide your own culling code." ([how BRG works](https://docs.unity3d.com/6000.2/Documentation/Manual/batch-renderer-group-how.html), [creating batches](https://docs.unity3d.com/6000.2/Documentation/Manual/batch-renderer-group-creating-batches.html))

### Bevy

- **Retained render world.** Entities with `SyncToSubWorld` (`SyncToRenderWorld`) get a render-world twin, linked by `MainEntity` and `RenderEntity`, and `SyncWorldPlugin` "is the first thing that runs every frame". ([sync_world.rs#L89](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_extract/src/sync_world.rs#L89)) Since 0.19, only mesh uniforms that changed are uploaded. Per-column change ticks gave a "132x speedup in our GPU mesh extraction code". ([0.19](https://bevy.org/news/bevy-0-19/), [0.20](https://bevy.org/news/bevy-0-20/))
- **CPU culling.** `check_visibility_cpu_culling` fills each view's `VisibleEntities` in `VisibilitySystems::CheckVisibility`, in the main world. `NoCpuCulling` on a camera or entity leaves the work to GPU culling. ([visibility/mod.rs#L61](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_camera/src/visibility/mod.rs#L61), [#L486](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_camera/src/visibility/mod.rs#L486))
- **Phases.** Each view has phases: opaque, transparent, shadow and others. Items are queued in `Queue` and sorted in `PhaseSort`, and each item names a `Draw` function, usually a tuple of `RenderCommand`s. ([render_phase/mod.rs#L1](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_phase/mod.rs#L1)) A `BinnedPhaseItem` has a `BinKey`, ordered "by the order of binding for best performance", and a `BatchSetKey`. Its items are made "just in time" and not stored. A `SortedPhaseItem` has a `SortKey`. ([#L2147](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_phase/mod.rs#L2147), [#L2195](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_phase/mod.rs#L2195)) `Opaque3dBatchSetKey` is `{pipeline, draw_function, material_bind_group_index, slabs, lightmap_slab}`, and `Opaque3dBinKey` is `{asset_id}`, the mesh. ([core_3d/mod.rs#L197](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_core_pipeline/src/core_3d/mod.rs#L197)) `BinnedRenderPhase` keeps multidrawable, batchable, unbatchable and non-mesh bins. On platforms with storage buffers, "a batch set always consists of at most one batch". ([render_phase/mod.rs#L109](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_phase/mod.rs#L109))
- **Mesh slabs.** `MeshAllocator` packs the vertex and index data of many meshes into shared buffers, "so that multiple meshes can be drawn back-to-back without any rebinding". Slabs default to 1 MiB minimum and 512 MiB maximum, grow by 1.5×, and data over 256 MiB gets a slab of its own. ([allocator.rs#L36](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/mesh/allocator.rs#L36), [slab_allocator.rs#L183](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/slab_allocator.rs#L183))
- **Draw.** The draw is `DrawMaterial = (SetItemPipeline, SetMeshViewBindGroup<0>, SetMeshViewBindingArrayBindGroup<1>, SetMeshBindGroup<2>, SetMaterialBindGroup<3>, DrawMesh)` ([material.rs#L588](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/material.rs#L588)). `TrackedRenderPass` "tracks the current pipeline state to skip redundant operations" ([draw_state.rs#L132](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_phase/draw_state.rs#L132)). `DrawMesh` makes a direct `draw_indexed(…, batch_range)`, or uses `multi_draw_indexed_indirect_count` or `multi_draw_indexed_indirect`. The comment says "We can't multi-draw in direct mode because `wgpu` doesn't expose that functionality." ([mesh.rs#L4715–L4800](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/mesh.rs#L4793))
- **GPU preprocessing.** `GpuPreprocessingMode` is `None` (no compute), `PreprocessingOnly` or `Culling`, the default. Under `PreprocessingOnly`, compute builds the mesh uniforms but nothing is culled or drawn indirectly, which is also what `NoIndirectDrawing` selects. ([gpu_preprocessing.rs#L150](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/batching/gpu_preprocessing.rs#L150)) The compute shader "expands each `MeshInputUniform` out to a full `MeshUniform` for each view", writes the previous transform for TAA, and frustum-culls. With occlusion culling, it runs twice, early and late. ([mesh_preprocess.wesl](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/mesh_preprocess.wesl#L1)) Without `multi_draw_indirect_count`, the parameter builder must "zero out the instance count" of culled draws ([build_indirect_params.wesl#L98](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/build_indirect_params.wesl#L98)). In 0.19, bin unpacking moved to the GPU, which the notes say saved almost 1.5 ms with a million cubes, and visibility-range LOD checks moved there too ([0.19](https://bevy.org/news/bevy-0-19/)).
- **Manual instancing.** `NoIndirectDrawing` on a camera lets the app "manually instance meshes as it sees fit", as the `custom_shader_instancing` example does ([view/mod.rs#L903](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/view/mod.rs#L903)).

### Godot

- **Server objects.** In 3D, "all visible objects are comprised of a resource and an instance": `instance_set_base(mesh)` and `instance_set_scenario(scenario)` ([RenderingServer.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/RenderingServer.xml#L13)).
- **Culling.** Each scenario has two `DynamicBVH` indexers, one for geometry and one for volumes, and `_scene_cull_threaded` splits the culling across threads ([renderer_scene_cull.h#L334](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_scene_cull.h#L334), [#L1153](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_scene_cull.h#L1153)). Occlusion culling uses `RendererSceneOcclusionCull::HZBuffer` ([renderer_scene_occlusion_cull.h#L45](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_scene_occlusion_cull.h#L45)).
- **Sort key.** Each surface caches `sort_key1` and `sort_key2`, packing `lod_index`, `depth_layer:4`, `surface_index:8`, `geometry_id:32`, `material_id:32`, `shader_id:32` and `priority:8`. The fields are ordered for "respecting priority and reducing the amount of rebinding of shaders, materials, and geometry". ([render_forward_clustered.h#L507](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.h#L507)) Opaque and motion lists use `sort_by_key()`, and alpha uses `sort_by_reverse_depth_and_priority()` ([render_forward_clustered.cpp#L1914](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp#L1914)).
- **Automatic instancing.** When an element's two keys equal the previous element's, and it is neither a MultiMesh nor a skinned instance and has the same mirroring, `repeats++` "count repeats to draw it using instancing", up to `MAX_REPEATS = (1 << 20) - 1`. The draw loop then issues one `draw_list_draw(…, instance_count)` and skips the equal elements. ([#L877](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp#L877), [#L598](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.cpp#L598)) The loop rebinds the pipeline, vertex and index arrays, transforms set and material set only when they change.
- **MultiMesh** is one object with one user-supplied AABB, culled as a whole, and the per-object light limit applies to all its instances ([MultiMesh.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/MultiMesh.xml)). `multimesh_allocate_data(…, use_indirect)` creates "an indirect command buffer … allowing the instance count to be modified directly on the GPU" ([RenderingServer.xml#L2704](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/RenderingServer.xml#L2704)).

### Frostbite (outside the FrameGraph talk)

- **2007.** The shading system is a "high-level platform-independent rendering API". At runtime, the user queues render blocks, the system looks up precomputed solutions, "blocks are sorted (category & depth)", and a "thin & dumb" back end sets the states. Undergrowth uses "standard stream instancing". (GDC 2007, slides 18, 35, 42)
- **2016.** GPU-driven triangle culling in compute: clusters of 256 triangles, "draw call compaction (no zero size draws)" by parallel prefix sum, and on DX12 "Count = Min(MaxCommandCount, pCountBuffer)" with a custom command signature. To find its source, "we can store the mesh section id along with each draw argument block". The fallback is "an instancing buffer with a step rate of 1". "Meshes within a batch share the same shader and strides." (GDC 2016, slides 19–35)

## 3. Per-object and per-material data, without push constants or bindless

| | Unity URP | Bevy 0.20 | Godot 4.7 | Frostbite |
|---|---|---|---|---|
| **Per view or frame** | global shader properties (`SetGlobalTextureAfterPass` in the graph); not studied further | group 0: `View` uniform at a dynamic offset, plus lights and clusters | set 0 scene-wide (lights, decals, global uniforms as a storage buffer); set 1 per render pass (`SceneDataBlock` uniform, instance buffer, atlases) | not covered |
| **Per object** | `UnityPerDraw`: "a large per-object GPU constant buffer" | group 2: `var<storage> mesh: array<Mesh>`, or `var<uniform> mesh: array<Mesh, N>` at a dynamic offset without storage buffers | `InstanceDataBuffer`: a storage buffer of `InstanceData` (transform, previous transform, AABB, flags, layer mask, instance-uniform offset) | 2016: mesh section id stored beside each draw's args |
| **How a draw finds its row** | not documented (see *Not verified*) | `instance_index`: a direct draw passes the batch's row range as its instance range | push constant `DrawCall.instance_index`, the base, plus `gl_InstanceIndex` | 2016: `StartInstanceLocation` added to `SV_InstanceID`, or a step-rate-1 instancing buffer |
| **Per material** | `UnityPerMaterial` CBUFFER, persistent in GPU memory | group 3: a bind group per material instance (non-bindless), or a slot in a bindless slab | set 3: a uniform buffer per material plus its textures, in one uniform set | not covered |
| **Per-instance user data** | `MaterialPropertyBlock` (breaks the SRP Batcher); BRG metadata (per-instance arrays in a raw buffer) | an extracted component as a uniform at a dynamic offset (`ComponentUniforms<C>`, `DynamicUniformIndex<C>`), as post effects use per view | `instance uniform` values in a global buffer at `instance_uniforms_ofs` | not covered |
| **Needs push constants** | no | only the GPU-culling path (wgpu's `IMMEDIATES`) and meshlets | yes: base instance index and the ubershader's specialisation | n/a |

### Unity URP

- **Constant buffers.** A compatible shader "must declare all built-in engine properties in a single constant buffer named `UnityPerDraw`", such as `unity_ObjectToWorld` and `unity_SHAr`. It must also declare "all material properties in a single constant buffer named `UnityPerMaterial`". A GameObject "mustn't use MaterialPropertyBlocks" and can't be a particle. ([SRP Batcher compatibility](https://docs.unity3d.com/6000.2/Documentation/Manual/SRPBatcher-Materials.html))
- **BRG data.** Each batch shares "a single GraphicsBuffer" (`GraphicsBuffer.Target.Raw` in the sample) and a set of `MetadataValue`s, each a property ID and a byte offset. The top bit (`0x80000000`) "instructs the shader that the data is an array with one value per instance". To change metadata, make a new batch. `SetBatchBuffer` swaps the buffer. ([creating batches](https://docs.unity3d.com/6000.2/Documentation/Manual/batch-renderer-group-creating-batches.html))
- **Dynamic branching.** `#pragma dynamic_branch` turns each keyword into a uniform integer, whose state Unity sends to the GPU every draw call. ([choose a branching type](https://docs.unity3d.com/6000.2/Documentation/Manual/shader-conditionals-choose-a-type.html))

### Bevy

- **Groups.** Group 0 holds `var<uniform> view: View`, bound with a dynamic offset (`uniform_buffer::<ViewUniform>(true)`, [mesh_view_bindings.rs#L261](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/mesh_view_bindings.rs#L261)). Group 1 holds environment maps, irradiance volumes and decals, as binding arrays or as single textures where binding arrays are missing ([mesh_view_bindings.wesl#L116](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/mesh_view_bindings.wesl#L116)). Group 2 holds the per-object array, a uniform array when `PER_OBJECT_BUFFER_BATCH_SIZE` is defined and a storage array otherwise ([mesh_bindings.wesl](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/mesh_bindings.wesl#L4)). Group 3 is the material (`MATERIAL_BIND_GROUP_INDEX = 3`, [material.rs#L75](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/material.rs#L75)). That is four groups, WebGPU's default `maxBindGroups`.
- **`GpuArrayBuffer<T>`** is a `BufferVec` storage buffer when the device has storage buffers. Otherwise it is a `BatchedUniformBuffer`, which groups "every N elements … into a batch as an `array<T, N>`" at a dynamic offset. That batch is capped at 1 MiB, and at 4 KiB on WebGL2, because larger uniform arrays compile slowly there. A draw that needs a different offset breaks the batch. ([gpu_array_buffer.rs#L38](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_resource/gpu_array_buffer.rs#L38), [batched_uniform_buffer.rs#L14](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_resource/batched_uniform_buffer.rs#L14), [render_phase/mod.rs#L150](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_phase/mod.rs#L150))
- **Uniform data per frame.** `DynamicUniformBuffer<T>` keeps values in RAM, std140-padded by `encase`, and `write_buffer` queues one copy to VRAM ([uniform_buffer.rs#L155](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_resource/uniform_buffer.rs#L155)). It is cleared and refilled each frame; this is the uniform-ring role.
- **Materials.** Without bindless, each material gets its own bind group, which holds its uniform buffers. A bind group becomes unprepared again when one of its shader buffers changes. ([material_bind_groups.rs#L224](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/material_bind_groups.rs#L224)) Bindless packs materials into slabs of binding arrays. In 0.19 it became "partial": "most materials, including StandardMaterial, do not need buffer array support". ([0.19](https://bevy.org/news/bevy-0-19/))

### Godot

- **Sets.** `SCENE_UNIFORM_SET = 0`, `RENDER_PASS_UNIFORM_SET = 1`, `TRANSFORMS_UNIFORM_SET = 2` and `MATERIAL_UNIFORM_SET = 3` ([render_forward_clustered.h#L64](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.h#L64)). Set 0 binding 13 is `GlobalShaderUniformData`, and set 1 binding 2 is `InstanceDataBuffer` ([scene_forward_clustered_inc.glsl#L259](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/forward_clustered/scene_forward_clustered_inc.glsl#L259), [#L369](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/shaders/forward_clustered/scene_forward_clustered_inc.glsl#L369)).
- **Per-draw data.** `PushConstant { base_index, uv_offset, multimesh_motion_vectors_current_offset, …previous_offset, ubershader {specialization, constants} }` and `InstanceData { transform[12], compressed_aabb_position/size, uv_scale, flags, instance_uniforms_ofs, gi_offset, layer_mask, prev_transform[12], lightmap_uv_scale }` ([render_forward_clustered.h#L326](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/render_forward_clustered.h#L326)). - **Material parameters.** Each material creates a uniform buffer with `uniform_buffer_create(ubo_size)`, fills it with `buffer_update` when its parameters change, and binds it in its uniform set ([material_storage.cpp#L1165](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/storage_rd/material_storage.cpp#L1165)).

## 4. What a material is

| | Unity URP | Bevy 0.20 | Godot 4.7 | Frostbite |
|---|---|---|---|---|
| **A material is** | an asset referencing one `Shader`, with property values and keywords | an asset implementing `Material: Asset + AsBindGroup + Clone`: a struct whose fields map to bindings, plus static shader choices | a `Resource`: `ShaderMaterial` (user code) or `StandardMaterial3D` (generated code), with parameters | 2007: a surface shader built as a graph |
| **Shader language** | HLSL in ShaderLab; passes picked by `LightMode` tag | WESL since 0.20 (`@if(DEF)` conditionals) | Godot shading language, compiled to GLSL and SPIR-V | 2007: graphs generating HLSL |
| **Variants** | keywords: `shader_feature` (only combinations materials use are built), `multi_compile` (all), `dynamic_branch` (uniform, no variant); `_local` scope | shader defs from the pipeline key (mesh key bits and the material's `bind_group_data`, such as `StandardMaterialKey`) | shader versions per pass (depth, depth with normal-roughness, colour, multiview…), specialisation constants, `StandardMaterial3D` code per `MaterialKey` | 2007: a "solution for each shading state combination", built offline |
| **Pipeline cache key** | engine-internal | `SpecializedMeshPipelines`: (vertex layout, key) → `CachedRenderPipelineId`; per entity, cached with change ticks | `PipelineKey {vertex format, framebuffer format, cull, primitive, version, color pass flags, specialization, wireframe, ubershader}` → hash → RID | n/a |
| **Compilation** | at draw, with driver disk caches; `GraphicsStateCollection` traces and prewarms PSOs (experimental) | asynchronous in `PipelineCache`; a draw is skipped until its pipeline is ready | on worker threads; ubershader pipelines draw while specialised ones compile; precompiled when meshes and shaders load (4.4+) | offline |
| **Sharing** | many materials share one variant (the SRP Batcher's unit) | `PipelineCache` does "not perform automatic deduplication of identical pipelines"; `SpecializedMeshPipelines` merges equal final vertex layouts | `StandardMaterial3D`s with one key share one shader (a counted `shader_map`) | n/a |

### Unity URP

- **Shader and variants.** "A material contains a reference to a Shader object." ([materials](https://docs.unity3d.com/6000.2/Documentation/Manual/materials-introduction.html)) `shader_feature` builds only the keyword combinations that materials in the build use, and an unbuilt combination falls back to the closest match. `multi_compile` builds every variant, for keywords scripts toggle at runtime. The page's example: eight keyword sets of three keywords can compile over 6,000 variants. ([choose a branching type](https://docs.unity3d.com/6000.2/Documentation/Manual/shader-conditionals-choose-a-type.html))
- **Keyword scope.** Local keywords are set through `Material.EnableKeyword`. `_local` directives keep global `Shader` calls from touching them. Global keywords are set with a `GlobalKeyword` and `Shader.EnableKeyword`; creating a `GlobalKeyword` is CPU-intensive, so the page advises doing it at load. `CommandBuffer.EnableKeyword` sets either kind. ([toggle keywords in scripts](https://docs.unity3d.com/6000.2/Documentation/Manual/shader-keywords-scripts.html))
- **PSOs.** `GraphicsStateCollection` records graphics states in a test build (`BeginTrace`/`EndTrace`), then `WarmUp` or `WarmUpProgressively` creates them on DX12, Metal and Vulkan, so drivers cache them. ([warm up PSOs](https://docs.unity3d.com/6000.2/Documentation/Manual/shader-prewarm.html))

### Bevy

- **The trait.** It has `vertex_shader`, `fragment_shader`, `prepass_*` and `deferred_*` (each a `ShaderRef`, `Default` meaning the mesh shader), plus `alpha_mode`, `opaque_render_method`, `depth_bias`, `enable_prepass`, `enable_shadows` and `specialize(pipeline, &mut descriptor, layout, key)`. `#[uniform(0)]`, `#[texture(1)]` and `#[sampler(2)]` derive the bind group. ([material.rs#L147](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/material.rs#L147)) The key is `MaterialPipelineKey { mesh_key: MeshPipelineKey, bind_group_data: M::Data }` ([#L490](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/material.rs#L490)). `StandardMaterialKey` packs cull mode, normal map, transmission, clearcoat, anisotropy, UV-channel bits and depth bias into 64 bits ([pbr_material.rs#L1251](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/pbr_material.rs#L1251)). The renderer erases the material type into `MaterialProperties` and `ErasedMaterialPipelineKey` in `bevy_material` ([lib.rs#L53](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_material/src/lib.rs#L53), [key.rs#L73](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_material/src/key.rs#L73)).
- **Caches.** `SpecializedMeshPipelines` is `HashMap<(MeshVertexBufferLayoutRef, Key), CachedRenderPipelineId>`. A miss specialises the descriptor, then deduplicates by its final `VertexBufferLayout`, since "different MeshVertexBufferLayouts can produce the same final VertexBufferLayout". ([pipeline_specializer.rs#L153](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_resource/pipeline_specializer.rs#L153), [#L240](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_resource/pipeline_specializer.rs#L240)) `PipelineCache` defers creation and "does not perform automatic deduplication of identical pipelines" ([pipeline_cache.rs#L219](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_resource/pipeline_cache.rs#L219)). `SetItemPipeline` returns `Skip` while a pipeline isn't ready. `ShaderCache` keeps `processed_shaders: HashMap<Box<[ShaderDefVal]>, Arc<ShaderModule>>` per shader asset, so one module exists per set of defines ([shader_cache.rs#L71](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_shader/src/shader_cache.rs#L71)). `SpecializedMaterialPipelineCache` stores each entity's pipeline id per view with the tick of its last change ([material.rs#L895](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/material.rs#L895)).
- **Other material types.** 0.20 added sprite materials and `ExtendedMaterial2d` ([0.20](https://bevy.org/news/bevy-0-20/)). `ExtendedMaterial` (base plus extension) exists for 3D ([extended_material.rs](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/extended_material.rs)).

### Godot

- **Generated shaders.** `BaseMaterial3D::MaterialKey` is a bitfield of every enum setting (transparency, blend, cull, depth draw, diffuse and specular mode, billboard, stencil…), a feature mask and flags, hashed and compared with `memcmp`. A static `HashMap<MaterialKey, ShaderData{RID shader; int users}> shader_map` shares one shader among all materials with a key. ([material.h#L358](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/resources/material.h#L358), [material.cpp#L656](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/resources/material.cpp#L656))
- **Variants.** Shader versions include the depth pass (with dual-paraboloid, normal-roughness, voxel GI, multiview, material and SDF variants) and the colour pass ([scene_shader_forward_clustered.h#L56](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/scene_shader_forward_clustered.h#L56)). `ShaderSpecialization` packs bits such as forward GI, light projector, soft shadows and sample counts ([#L103](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/scene_shader_forward_clustered.h#L103)).
- **Pipelines.** `PipelineKey` is hashed with murmur3 into a `PipelineHashMapRD`, whose compilations run as `WorkerThreadPool` tasks ([#L191](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/forward_clustered/scene_shader_forward_clustered.h#L191), [pipeline_hash_map_rd.h](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/servers/rendering/renderer_rd/pipeline_hash_map_rd.h#L43)). Since 4.4, Godot tries to precompile at load the pipelines it detects. Ubershaders take specialisation values at render time, through the `PushConstantUbershader` above, so specialised pipelines compile in the background. Drivers cache pipelines on disk. In 4.5, a shader baker ships the intermediate format. All of this applies to Forward+ and Mobile on Vulkan, D3D12 and Metal, not Compatibility. ([pipeline compilations](https://docs.godotengine.org/en/stable/tutorials/performance/pipeline_compilations.html))

### Frostbite (GDC 2007)

- **Surface shaders.** Surface shaders are "graph-based instead of code", and instance shaders are graphs used as nodes, like functions. High-level states hide "shader permutation hell". The offline pipeline generates a "solution for each shading state combination", each with its complete state setup and generated HLSL vertex and pixel shaders. About 500 hand-written shaders for ToyShop motivated it. (slides 4, 22–34)

## 5. Handles and ownership

| | Unity URP | Bevy 0.20 | Godot 4.7 | Frostbite FrameGraph |
|---|---|---|---|---|
| **A user holds** | managed references to `UnityEngine.Object`s (Mesh, Material, Texture); per frame, render graph `TextureHandle`, `BufferHandle` and `RendererListHandle` | `Handle<T>` in components (`Mesh3d(Handle<Mesh>)`, `MeshMaterial3d<M>(Handle<M>)`); `AssetId<T>` for lookups | `RID`s from `*_create`, usually through a `Resource` that holds them | graph handles returned by `createTexture`, `read` and `write` |
| **Shape** | object: a managed wrapper of a native object with an instance ID; `TextureHandle`: a struct of index (16 bits), version (15 bits) and execution stamp (32 bits) | `Handle::Strong(Arc<StrongHandle>)` or `Handle::Uuid`; `AssetId::Index{generation, index}` or `Uuid`, `Copy` | `uint64`: validator (high 32) and index (low 32); 0 is invalid; "only useful during the current session" | virtual resource handles, versioned on write |
| **Who owns what they name** | the engine's native side; `Destroy` detaches the wrapper, which then compares equal to `null`; Addressables count references; the graph owns created textures, others own imported ones | `Assets<T>` owns the data; strong handles keep it alive; the render world keeps GPU copies keyed by `AssetId` | the server owns the object; `free_rid` frees it; a `Resource` (ref-counted) frees its RID in its destructor | the graph owns transients for one frame; imported resources belong to their modules |
| **Lifetime check** | detached-object `==` override; handle validity bit compared with the current execution | generation in `AssetIndex`; a strong handle's drop is counted | validator compared on lookup | graph-local: valid during setup and execute of one frame |

- **Unity.** "Each instance of a class that derives from UnityEngine.Object is linked to a counterpart native object." A destroyed one is "detached": it keeps its instance ID, and `== null` is true while `ReferenceEquals(obj, null)` is false. ([Object](https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/object)) Addressables "keeps a reference count of every item it loads", but memory is freed only when the whole AssetBundle unloads ([Addressables 2.3.16 memory](https://docs.unity3d.com/Packages/com.unity.addressables@2.3/manual/MemoryManagement.html)). Render graph handles "do not need to be disposed/freed (they are auto-invalidated at the end of graph execution)". Each one carries an execution index, because pooled `PassData` objects "can contain stale handles from a previous render graph execution". ([RenderGraphResourceTexture.cs#L92](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/RenderGraphResourceTexture.cs#L92), [RenderGraphResources.cs#L18](https://github.com/Unity-Technologies/Graphics/blob/0efc28ea742b1966b9dd9cc4489e58b986a13faf/Packages/com.unity.render-pipelines.core/Runtime/RenderGraph/RenderGraphResources.cs#L18))
- **Bevy.** A strong handle keeps its asset "alive until the [`Handle`] is dropped", and "modifying the *asset* … will change the asset for all handles referencing it" ([handle.rs#L115](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_asset/src/handle.rs#L115)). An `AssetId` is "cheap to Copy/Clone and is not directly tied to the lifetime of the Asset", and its `AssetIndex` is `{generation: u32, index: u32}` ([id.rs#L23](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_asset/src/id.rs#L23), [assets.rs#L23](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_asset/src/assets.rs#L23)). A `RenderAsset` turns its source asset into a GPU form in `PrepareAssets` ([render_asset.rs#L47](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_asset.rs#L47)). `RenderAssetUsages` says whether the CPU copy is dropped after upload (`RENDER_WORLD` alone) or kept (`MAIN_WORLD | RENDER_WORLD`) ([bevy_asset render_asset.rs#L32](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_asset/src/render_asset.rs#L32)). GPU wrappers such as `Texture { id, value }` are cloneable and carry a unique id ([texture.rs#L32](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_resource/texture.rs#L32)). Since 0.19, `RenderStartup` runs "every time a new `RenderDevice` is acquired", to recreate GPU resources after a device loss ([lib.rs#L246](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/lib.rs#L246)). In 0.19, handles became serialisable by asset path ([0.19](https://bevy.org/news/bevy-0-19/)).
- **Godot.** `RID` is a `uint64_t _id`, with `get_local_index()` returning the low 32 bits ([rid.h#L38](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/core/templates/rid.h#L38)). `RID_Alloc` puts a random validator in the high 32 bits and checks it on every lookup ([rid_owner.h#L109](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/core/templates/rid_owner.h#L109)). RIDs "are opaque" and "only useful during the current session" ([RID.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/RID.xml)). Server objects are created by `*_create` and freed with `free_rid` ([RenderingServer.xml#L1628](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/RenderingServer.xml#L1628)). `Material::~Material` frees its RID ([material.cpp#L188](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/scene/resources/material.cpp#L188)). Resources "are reference-counted and freed when no longer in use", and a global cache by path returns the cached resource on a second load ([Resource.xml](https://github.com/godotengine/godot/blob/ed1daf0bf001b61586d9930840f2f1394092c079/doc/classes/Resource.xml)). The RenderingDevice postpones frees until frames in flight finish, and freeing a shader frees its pipelines ([The Compositor](https://docs.godotengine.org/en/stable/tutorials/rendering/compositor.html)).
- **Frostbite.** Setup "handles" resolve to real resources only in execute, through `resources.getTexture(data.input)`. Modules pass handles to one another in blackboard structs (slides 29, 35, 37).

## 6. On WebGPU and wgpu

Bevy is the only one of the four already on wgpu. Facts that bear on draw over gfx:

- **What gfx has.** gfx is designed against WebGPU's default limits: 4 bind groups, 8 dynamic uniform and 4 dynamic storage buffers per pipeline layout, 8 storage buffers and 4 storage textures per stage, 64 KiB uniform bindings, 128 MiB storage bindings, and 256-byte offset alignment ([gfx `DefaultLimits`](../../../gfx/descriptors.go#L409), [spec limits](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#limits)). A dynamic offset "must be a multiple of `minUniformBufferOffsetAlignment`" ([setBindGroup](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#dom-gpubindingcommandsmixin-setbindgroup)). gfx mirrors `SetBindGroup(index, group, dynamicOffsets)`, `MultiDrawIndirect` and `MultiDrawIndexedIndirect` (no count), and `FeatureFlagIndirectFirstInstance` and `FeatureFlagMultiDrawIndirect` ([encoders.go#L51](../../../gfx/encoders.go#L51), [enums.go#L91](../../../gfx/enums.go#L91)). It leaves the uniform ring, transient-target pool and pipeline sharing to the layer above ([gfx design](../../../gfx/docs/design.md#writes-and-transient-memory)).
- **The row index without push constants.** WebGPU's direct draws take any `firstInstance`. In `drawIndirect`, though, "the value corresponding to firstInstance must be 0, unless the 'indirect-first-instance' feature is enabled", or the call "will be treated as a no-op" ([drawIndirect](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#dom-gpurendercommandsmixin-drawindirect)). Bevy's direct path reaches each object's row through `instance_index` alone: `draw_indexed(…, batch_range)`, then `mesh[instance_index]`. Godot needs a push constant for the base index.
- **Bevy's indirect path is gated.** It needs `INDIRECT_FIRST_INSTANCE | IMMEDIATES` (wgpu's push constants), at least 10 storage buffers and 12 storage textures per stage, and compute. Otherwise Bevy drops to `PreprocessingOnly`: compute builds the mesh uniforms, and draws stay direct and instanced. It also drops on the GL backend and on some Android drivers. ([gpu_preprocessing.rs#L1545](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/batching/gpu_preprocessing.rs#L1545)) WebGPU's defaults are 8 and 4, and WebGPU has no push constants, so on gfx's default limits Bevy would take the direct path.
- **Multi-draw without a count.** Without a count buffer, Bevy multi-draws the whole batch set and relies on zeroed instance counts for culled draws ([mesh.rs#L4793](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/mesh.rs#L4793), [build_indirect_params.wesl#L98](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/build_indirect_params.wesl#L98)). Frostbite's 2016 talk notes that "efficiency drops as we hit a string of empty draws" (slide 32).
- **Without storage buffers,** Bevy's per-object data falls back to uniform arrays at dynamic offsets, and batches break at each new offset ([gpu_array_buffer.rs#L38](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/render_resource/gpu_array_buffer.rs#L38)). Core WebGPU allows 8 storage buffers in the vertex stage by default (`maxStorageBuffersInVertexStage`); only compatibility mode, which gfx does not use, defaults to 0 ([spec limits](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#limits)).
- **Bevy's binding budget.** Its mesh pipeline uses exactly four bind groups (view, view binding arrays or single textures, mesh, material). Its view-level binding arrays have single-texture fallbacks. Its materials fall back to one bind group per material when bindless is unavailable. ([mesh_view_bindings.wesl#L116](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_pbr/src/render/mesh_view_bindings.wesl#L116), [material_bind_groups.rs#L85](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/material_bind_groups.rs#L85)) Bevy wraps `create_render_bundle_encoder` but nothing in `bevy_render` or `bevy_pbr` calls it ([render_device.rs#L145](https://github.com/bevyengine/bevy/blob/a0577b5c6a7b208719dd761c5c6a7a539e472a97/crates/bevy_render/src/renderer/render_device.rs#L145)).
- **No memory aliasing in WebGPU.** WebGPU has no heaps or placed resources: its "aliasing" rules are about bindings of one resource. Frostbite-style memory aliasing cannot be expressed. Reusing whole textures by descriptor, as URP and Bevy do, can ([spec, texture-view aliasing](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#texture-view-aliasing)). gfx's release is immediate and reference-counted, and reuse across frames is ordered on the queue ([gfx design](../../../gfx/docs/design.md#writes-and-transient-memory)).
- **Specialisation constants.** These play the role of Godot's specialisation constants and Bevy's shader defs at pipeline creation. WebGPU's `GPUProgrammableStage.constants` sets a module's `override` declarations ([spec](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#dom-gpuprogrammablestage-constants)). gfx today mirrors `Constants` only on `ComputePipelineDescriptor`. Its render `VertexState` and `FragmentState` have none ([descriptors.go#L180](../../../gfx/descriptors.go#L180), [#L263](../../../gfx/descriptors.go#L263)). Godot's ubershader trick passes specialisation through push constants, which WebGPU lacks.
- **The wgpu fork, at `5a49474` (0.34.13).**
  - `FeatureIndirectFirstInstance` is advertised by Vulkan (when the device has `drawIndirectFirstInstance`) and GLES. DX12 and Metal do not advertise it ([hal/vulkan/api.go#L560](https://github.com/dvoyni/wgpu/blob/5a494744afef6cb97f0306790962c61ef02fb3f7/hal/vulkan/api.go#L558); no entry in [hal/dx12/adapter.go](https://github.com/dvoyni/wgpu/blob/5a494744afef6cb97f0306790962c61ef02fb3f7/hal/dx12/adapter.go) or [hal/metal/adapter.go](https://github.com/dvoyni/wgpu/blob/5a494744afef6cb97f0306790962c61ef02fb3f7/hal/metal/adapter.go)).
  - `FeatureMultiDrawIndirect` is advertised by Vulkan, DX12 and GLES. Since v0.30.23, "Vulkan multi-draw calls fall back to exact loops when unavailable or over the device limit" ([CHANGELOG#L979](https://github.com/dvoyni/wgpu/blob/5a494744afef6cb97f0306790962c61ef02fb3f7/CHANGELOG.md#L979), [hal/dx12/adapter.go#L261](https://github.com/dvoyni/wgpu/blob/5a494744afef6cb97f0306790962c61ef02fb3f7/hal/dx12/adapter.go#L261)).
  - v0.34.7 stopped refusing a non-zero `firstInstance` on direct draws, which WebGPU allows ([CHANGELOG#L275](https://github.com/dvoyni/wgpu/blob/5a494744afef6cb97f0306790962c61ef02fb3f7/CHANGELOG.md#L275)).
  - Since v0.34.3, the fork has `MultiDrawIndirectCount` and `MultiDrawIndexedIndirectCount` behind `FeatureMultiDrawIndirectCount`, which only Vulkan 1.2+ advertises ([CHANGELOG#L491](https://github.com/dvoyni/wgpu/blob/5a494744afef6cb97f0306790962c61ef02fb3f7/CHANGELOG.md#L491), [api.go#L566](https://github.com/dvoyni/wgpu/blob/5a494744afef6cb97f0306790962c61ef02fb3f7/hal/vulkan/api.go#L566)). gfx, designed on v0.34.2, leaves indirect-count out ([gfx design](../../../gfx/docs/design.md#types-descriptors-and-handles)).
- **Godot's CompositorEffect example is compute-first.** Its sample effect writes the colour image in place as a storage image (`UNIFORM_TYPE_IMAGE`) ([The Compositor](https://docs.godotengine.org/en/stable/tutorials/rendering/compositor.html)). In WebGPU, a texture written from compute needs `STORAGE_BINDING` usage and counts against `maxStorageTexturesPerShaderStage`, 4 by default. A `bgra8unorm` texture allows that usage only with the `bgra8unorm-storage` feature ([spec §25.13](https://www.w3.org/TR/2026/CRD-webgpu-20260915/#bgra8unorm-storage)), which gfx mirrors as `FeatureFlagBGRA8UnormStorage`.

- **`CommonOpaque` flags.** The exact flags inside `SortingCriteria.CommonOpaque` and `CommonTransparent` are not listed on their page.
- **BRG off-SSBO.** BRG's constant-buffer mode on platforms without storage buffers was not covered by the pages read.
- **Plain GPU instancing in URP.** Per-instance property arrays (`UNITY_INSTANCING_BUFFER`) were not read for URP.
- **Frostbite today.** Frostbite's current draw gathering, per-object data, materials and handles are not in the FrameGraph talk. The 2007 and 2016 talks cited above describe older engines. The FrameGraph slides were read through SlideShare's transcript, not the PDF from GDC Vault.
- **Godot's occlusion buffer.** Whether Godot's occlusion `HZBuffer` is rasterised with Embree on the CPU was not read in source; only the class was located.
